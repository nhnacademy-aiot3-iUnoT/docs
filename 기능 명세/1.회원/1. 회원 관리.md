# 📝 1.1 계정 생성

## 기능 목적

> 이름, 이메일, 비밀번호를 입력받아 신규 계정을 생성한다.

## 사용자 및 권한

* 비인증 사용자

## 사전 조건

* 동일한 이메일을 사용하는 계정이 없어야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `name` | 문자열 | O | 최대 16자 |
| `email` | 이메일 | O | 최대 32자, 중복 불가 |
| `password` | 문자열 | O | 6자 이상 64자 이하 |

## 처리 절차

1. 이름, 이메일, 비밀번호 입력값을 검증한다.
2. 이메일 중복 여부를 확인한다.
3. 계정 식별에 사용할 UUID를 생성한다.
4. 비밀번호를 해싱한다.
5. 계정 권한을 `USER`로 설정한다.
6. 계정 상태를 `ACTIVE`로 설정한다.
7. 계정을 저장한다.
8. `createdAt`, `updatedAt`을 기록한다.

## 업무 규칙

* UUID는 외부 계정 식별자와 JWT Subject로 사용한다.
* UUID는 계정 생성 이후 변경할 수 없다.
* 비밀번호는 평문으로 저장하지 않는다.
* 일반 회원가입을 통해 `ADMIN` 계정을 생성할 수 없다.
* 사전에 이메일 중복 확인을 수행했더라도 계정 생성 시 중복 여부를 다시 검증한다.
* 애플리케이션 중복 검사와 별개로 데이터베이스에 이메일 Unique 제약조건을 적용한다.

## 처리 결과

* `USER` 권한과 `ACTIVE` 상태를 가진 신규 계정이 생성된다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 입력값이 제약사항을 만족하지 않는 경우 | 입력값 오류를 반환한다. |
| 이메일이 이미 사용 중인 경우 | 이메일 중복 오류를 반환한다. |
| 계정 저장 중 이메일 Unique 제약조건 위반이 발생한 경우 | 이메일 중복 오류를 반환한다. |

# 📝 1.2 이메일 중복 확인

## 기능 목적

> 회원가입 전에 이메일 사용 가능 여부를 확인한다.

## 사용자 및 권한

* 비인증 사용자
* `USER`
* `ADMIN`

## 사전 조건

* 확인할 이메일이 이메일 입력 형식을 만족해야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `email` | 이메일 | O | 최대 32자 |

## 처리 절차

1. 이메일 입력값을 검증한다.
2. 동일한 이메일을 사용하는 계정이 존재하는지 확인한다.
3. 이메일 사용 가능 여부를 반환한다.

## 업무 규칙

* 이메일 중복 확인 요청에서는 계정 정보를 변경하지 않는다.
* 이메일 중복 확인 결과는 해당 이메일의 사용을 예약하거나 보장하지 않는다.
* 계정 생성 시 이메일 중복 여부를 다시 검증한다.
* 탈퇴 처리로 기존 계정의 이메일이 제거된 경우 해당 이메일을 다시 사용할 수 있다.
* 이메일 외의 계정 정보는 반환하지 않는다.

## 처리 결과

| 결과 | 설명 |
| --- | --- |
| 사용 가능 | 동일한 이메일을 사용하는 계정이 존재하지 않는다. |
| 사용 불가 | 동일한 이메일을 사용하는 계정이 존재한다. |

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 이메일이 입력되지 않은 경우 | 입력값 오류를 반환한다. |
| 이메일 형식 또는 길이 제약사항을 만족하지 않는 경우 | 입력값 오류를 반환한다. |

# 📝 1.3 내 계정 정보 조회

## 기능 목적

> 인증된 사용자가 자신의 계정 정보를 조회한다.

## 사용자 및 권한

* `USER`
* `ADMIN`

## 사전 조건

* 요청 사용자의 인증 정보가 유효해야 한다.
* JWT Subject에 해당하는 계정이 존재해야 한다.

## 입력값

* 별도의 계정 식별 정보를 입력받지 않는다.
* JWT Subject를 통해 본인 계정을 식별한다.

## 처리 절차

1. 요청 사용자의 인증 정보를 확인한다.
2. JWT Subject를 통해 본인 계정을 조회한다.
3. 조회된 계정 정보를 반환한다.

## 업무 규칙

* DB 내부 식별자인 `id`는 외부에 노출하지 않는다.
* 다른 사용자의 UUID를 조회 대상으로 입력받지 않는다.
* 비밀번호와 비밀번호 해시값은 반환하지 않는다.
* 본인 계정 조회는 유효한 인증 정보를 가진 계정에 한해 허용한다.
* 관리자가 다른 계정을 조회하는 기능은 `회원권한.md`의 관리자 계정 조회 정책을 따른다.

## 처리 결과

* 다음 계정 정보가 반환된다.
  * UUID
  * 이름
  * 이메일
  * 권한
  * 계정 상태
  * 생성 일시
  * 수정 일시
  * 탈퇴 일시

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 인증 정보가 유효하지 않은 경우 | 인증 오류를 반환한다. |
| 계정이 존재하지 않는 경우 | 계정 조회 오류를 반환한다. |

# 📝 1.4 새 비밀번호 사용 가능 여부 확인

## 기능 목적

> 사용자가 변경하려는 새 비밀번호가 현재 사용 중인 비밀번호와 동일한지 미리 확인한다.

## 사용자 및 권한

* `USER`
* `ADMIN`

## 사전 조건

* 요청 사용자의 인증 정보가 유효해야 한다.
* 대상 계정이 존재해야 한다.
* 계정 상태가 `ACTIVE`여야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `newPassword` | 문자열 | O | 변경하려는 새 비밀번호, 6자 이상 64자 이하 |

## 처리 절차

1. JWT Subject를 통해 요청 사용자의 계정을 조회한다.
2. 새 비밀번호의 입력값을 검증한다.
3. 비밀번호 인코더를 사용하여 새 비밀번호와 현재 비밀번호 해시를 비교한다.
4. 현재 비밀번호와의 동일 여부에 따라 사용 가능 결과를 반환한다.
5. 계정 정보는 변경하지 않는다.

## 업무 규칙

* 이 기능은 최종 수정 요청 전 사용자 편의를 위해 제공하는 사전 검증 기능이다.
* 확인 요청에서는 비밀번호를 변경하지 않는다.
* 확인 요청으로 DB의 계정 정보를 수정하지 않는다.
* 새 비밀번호가 현재 비밀번호와 동일한 경우 사용할 수 없다.
* 비밀번호 비교에는 비밀번호 인코더의 검증 기능을 사용한다.
* 입력된 비밀번호를 로그 또는 별도 저장소에 기록하지 않는다.
* 확인 성공 여부를 계정 수정 권한으로 사용하지 않는다.
* 일회성 검증 토큰을 발급하지 않는다.
* 사전 확인을 수행하지 않아도 최종 수정 요청을 보낼 수 있다.
* 최종 수정 요청에서 동일 여부를 다시 검증한다.

## 처리 결과

| 결과 | 설명 |
| --- | --- |
| 사용 가능 | 새 비밀번호가 현재 비밀번호와 다르다. |
| 사용 불가 | 새 비밀번호가 현재 비밀번호와 동일하다. |

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 인증 정보가 유효하지 않은 경우 | 인증 오류를 반환한다. |
| 계정이 존재하지 않는 경우 | 계정 조회 오류를 반환한다. |
| 계정 상태가 `ACTIVE`가 아닌 경우 | 확인 요청을 거부한다. |
| 새 비밀번호가 입력되지 않은 경우 | 입력값 오류를 반환한다. |
| 새 비밀번호가 입력 정책을 만족하지 않는 경우 | 입력값 오류를 반환한다. |
| 새 비밀번호가 현재 비밀번호와 동일한 경우 | 동일 비밀번호 사용 오류 또는 사용 불가 결과를 반환한다. |

# 📝 1.5 내 계정 정보 수정

## 기능 목적

> 인증된 사용자가 자신의 이름 또는 비밀번호를 변경한다.

## 사용자 및 권한

* `USER`: 자신의 계정 정보만 수정할 수 있다.
* `ADMIN`: 자신의 계정 정보만 수정할 수 있다.

## 사전 조건

* 요청 사용자의 인증 정보가 유효해야 한다.
* 대상 계정이 존재해야 한다.
* 계정 상태가 `ACTIVE`여야 한다.
* 이름 또는 새 비밀번호 중 하나 이상의 변경값이 있어야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `name` | 문자열 | 변경 시 O | 최대 16자 |
| `newPassword` | 문자열 | 변경 시 O | 6자 이상 64자 이하 |

## 처리 절차

1. JWT Subject를 통해 수정 대상 계정을 조회한다.
2. 계정 상태가 `ACTIVE`인지 확인한다.
3. 변경할 입력값을 검증한다.
4. 새 비밀번호가 포함된 경우 현재 비밀번호와 동일한지 다시 확인한다.
5. 새 비밀번호가 현재 비밀번호와 다르면 해싱한다.
6. 변경된 이름 또는 비밀번호를 계정에 반영한다.
7. `updatedAt`을 갱신한다.
8. 변경 결과를 저장한다.

## 업무 규칙

* `ACTIVE` 상태의 계정만 정보를 수정할 수 있다.
* 사용자는 자신의 계정 정보만 수정할 수 있다.
* `ADMIN`이라도 다른 사용자의 이름이나 비밀번호를 직접 변경할 수 없다.
* UUID, 이메일, 권한, 계정 상태 및 `createdAt`은 일반 계정 정보 수정으로 변경할 수 없다.
* 이메일은 계정 정보 수정 대상으로 제공하지 않는다.
* 새 비밀번호 사용 가능 여부 확인 기능의 호출 여부를 신뢰하지 않는다.
* 최종 수정 요청에서 새 비밀번호와 현재 비밀번호의 동일 여부를 다시 검증한다.
* 새 비밀번호가 현재 비밀번호와 동일하면 비밀번호를 변경하지 않는다.
* 새 비밀번호는 해싱한 후 저장한다.
* 이름만 변경하는 경우 비밀번호 검증을 수행하지 않는다.
* 이름과 비밀번호를 함께 변경할 수 있다.
* 입력된 비밀번호를 로그에 기록하지 않는다.

## 처리 결과

* 요청된 이름 또는 비밀번호가 변경된다.
* `updatedAt`이 갱신된다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 인증 정보가 유효하지 않은 경우 | 인증 오류를 반환한다. |
| 계정이 존재하지 않는 경우 | 계정 수정 오류를 반환한다. |
| 계정 상태가 `ACTIVE`가 아닌 경우 | 계정 정보 수정을 거부한다. |
| 변경할 값이 없는 경우 | 입력값 오류를 반환한다. |
| 입력값이 제약사항을 만족하지 않는 경우 | 입력값 오류를 반환한다. |
| 새 비밀번호가 현재 비밀번호와 동일한 경우 | 동일 비밀번호 사용 오류를 반환한다. |
| 계정 정보 저장 중 오류가 발생한 경우 | 변경 내용을 롤백하고 오류를 반환한다. |

# 📝 1.6 비활성 계정 재활성화

## 기능 목적

> 계정 소유자가 이메일 인증을 완료하여 자신의 비활성 계정을 다시 활성화한다.

## 사용자 및 권한

* 이메일 인증을 완료한 계정 소유자

## 사전 조건

* 대상 계정이 `INACTIVE` 상태여야 한다.
* 계정에 등록된 이메일로 인증 코드를 수신할 수 있어야 한다.
* 유효한 인증 코드를 입력해야 한다.

## 입력값

### 인증 코드 발급 요청

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `email` | 이메일 | O | 계정에 등록된 이메일 |

### 재활성화 요청

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `email` | 이메일 | O | 계정에 등록된 이메일 |
| `verificationCode` | 문자열 | O | 이메일로 발급된 인증 코드 |

## 처리 절차

### 인증 코드 발급

1. 이메일 입력값을 검증한다.
2. 이메일에 해당하는 계정이 `INACTIVE` 상태인지 확인한다.
3. 재활성화 인증 코드를 생성한다.
4. 인증 코드의 유효기간과 사용 상태를 저장한다.
5. 인증 코드를 계정 이메일로 발송한다.

### 재활성화

1. 이메일과 인증 코드를 확인한다.
2. 인증 코드가 유효기간 내에 발급된 코드인지 확인한다.
3. 인증 코드가 이미 사용되었는지 확인한다.
4. 대상 계정이 `INACTIVE` 상태인지 확인한다.
5. 계정 상태를 `ACTIVE`로 변경한다.
6. 인증 코드를 사용 완료 상태로 변경한다.
7. `updatedAt`을 갱신한다.

## 업무 규칙

* `USER`는 자신의 계정을 직접 `INACTIVE` 상태로 변경할 수 없다.
* `INACTIVE` 계정만 재활성화할 수 있다.
* 계정 소유자는 이메일 인증을 완료한 경우에만 자신의 계정을 재활성화할 수 있다.
* `INACTIVE` 계정은 재활성화 전까지 로그인할 수 없다.
* 휴면 상태에서도 재활성화를 위해 이메일을 유지한다.
* 인증 코드에는 유효기간을 적용한다.
* 인증 코드는 한 번만 사용할 수 있다.
* 인증 코드 원문은 장기간 보관하지 않는다.
* 인증 코드 검증 실패 횟수를 제한할 수 있어야 한다.
* 인증 코드 발급 응답으로 계정 존재 여부가 불필요하게 노출되지 않도록 한다.
* 새로운 인증 코드를 발급하면 기존 인증 코드를 무효화할 수 있다.
* `LOCKED` 계정은 휴면 해제 절차로 잠금을 해제할 수 없다.
* `WITHDRAWN` 계정은 재활성화할 수 없다.
* 관리자가 계정을 재활성화하는 기능은 `회원권한.md`를 따른다.

## 처리 결과

* 계정 상태가 `ACTIVE`로 변경된다.
* 인증 코드가 사용 완료 처리된다.
* `updatedAt`이 갱신된다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 계정이 존재하지 않는 경우 | 일반화된 인증 코드 발급 결과를 반환한다. |
| 계정 상태가 `INACTIVE`가 아닌 경우 | 상태 변경을 거부한다. |
| 인증 코드가 일치하지 않는 경우 | 인증 코드 오류를 반환한다. |
| 인증 코드가 만료된 경우 | 인증 코드 만료 오류를 반환한다. |
| 인증 코드가 이미 사용된 경우 | 인증 코드 오류를 반환한다. |
| 인증 시도 횟수를 초과한 경우 | 인증 요청을 일시적으로 제한한다. |

# 📝 1.7 계정 탈퇴

## 기능 목적

> 계정 소유자가 본인 확인을 완료한 후 계정을 탈퇴 상태로 변경하고 개인정보를 제거한다.

## 사용자 및 권한

* `USER`: 자신의 계정을 탈퇴할 수 있다.
* `ADMIN`: 자신의 계정을 탈퇴할 수 있다.

## 사전 조건

* 대상 계정이 존재해야 한다.
* 대상 계정이 `WITHDRAWN` 상태가 아니어야 한다.
* 요청 사용자가 탈퇴 대상 계정의 소유자여야 한다.
* 서비스 정책에 따른 본인 확인을 완료해야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `password` | 문자열 | O | 본인 확인과 탈퇴 의사 재확인을 위한 현재 비밀번호 |

## 계정 식별 방식

* `ACTIVE` 계정은 JWT Subject를 통해 탈퇴 대상 계정을 식별한다.
* `LOCKED` 또는 `INACTIVE` 계정이 유효한 인증 정보를 사용할 수 없는 경우 별도의 본인 확인 절차를 통해 계정을 식별한다.
* 요청 사용자가 임의의 UUID를 전달하여 다른 계정을 탈퇴시킬 수 없도록 한다.

## 처리 절차

1. 탈퇴 대상 계정을 식별한다.
2. 계정이 존재하는지 확인한다.
3. 계정 상태가 `WITHDRAWN`인지 확인한다.
4. 요청자가 탈퇴 대상 계정의 소유자인지 확인한다.
5. 입력한 비밀번호 또는 별도의 본인 확인 수단을 검증한다.
6. 계정 상태를 `WITHDRAWN`으로 변경한다.
7. 이름, 이메일 및 비밀번호 정보를 제거한다.
8. 발급된 Refresh Token을 폐기한다.
9. 적용된 Access Token 무효화 정책에 따라 기존 토큰을 처리한다.
10. `withdrawnAt`과 `updatedAt`을 기록한다.
11. 탈퇴 처리 결과를 저장한다.

## 업무 규칙

* `ACTIVE`, `LOCKED`, `INACTIVE` 상태의 계정은 탈퇴할 수 있다.
* `WITHDRAWN` 상태의 계정은 다시 탈퇴할 수 없다.
* `WITHDRAWN`은 복구할 수 없는 최종 상태이다.
* 계정 상태와 관계없이 탈퇴 전에 계정 소유자 본인 확인을 수행해야 한다.
* `LOCKED` 또는 `INACTIVE` 계정은 계정을 `ACTIVE`로 변경하지 않고 바로 탈퇴할 수 있다.
* 현재 비밀번호 검증에는 비밀번호 인코더의 검증 기능을 사용한다.
* 계정 식별과 이력 유지를 위해 DB 내부 `id`와 UUID는 유지한다.
* 이름, 이메일, 비밀번호 등의 개인정보는 제거하거나 복구할 수 없는 형태로 처리한다.
* 탈퇴한 계정의 권한은 더 이상 사용할 수 없다.
* 탈퇴한 계정은 로그인하거나 재활성화할 수 없다.
* 이메일이 제거된 이후 해당 이메일을 신규 계정에서 다시 사용할 수 있다.
* 계정 상태 변경과 개인정보 제거는 하나의 트랜잭션으로 처리한다.
* 탈퇴 처리 중 오류가 발생하면 상태 변경과 개인정보 제거를 모두 롤백한다.

## 인증 토큰 처리 규칙

* 해당 계정에 발급된 Refresh Token은 탈퇴 즉시 폐기한다.
* JWT Access Token은 발급 후 서명 검증만으로 즉시 폐기할 수 없다.
* 기존 Access Token을 즉시 차단하려면 다음 정책 중 하나를 적용한다.
  * 토큰 식별자를 이용한 블랙리스트
  * 계정별 토큰 버전 검증
  * 보호 자원 요청 시 계정 상태 확인
* 별도의 즉시 폐기 정책을 사용하지 않는 경우 Access Token의 만료 시간을 짧게 설정한다.

## 처리 결과

* 계정 상태가 `WITHDRAWN`으로 변경된다.
* 계정의 개인정보가 제거된다.
* Refresh Token이 폐기된다.
* `withdrawnAt`과 `updatedAt`이 기록된다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 계정이 존재하지 않는 경우 | 계정 조회 오류를 반환한다. |
| 이미 탈퇴한 계정인 경우 | 중복 탈퇴 요청을 거부한다. |
| 요청자가 계정 소유자가 아닌 경우 | 접근 권한 오류를 반환한다. |
| 비밀번호가 입력되지 않은 경우 | 입력값 오류를 반환한다. |
| 비밀번호 또는 본인 확인 정보가 일치하지 않는 경우 | 본인 확인 오류를 반환한다. |
| 개인정보 제거 또는 상태 변경 중 오류가 발생한 경우 | 전체 탈퇴 처리를 롤백하고 오류를 반환한다. |
