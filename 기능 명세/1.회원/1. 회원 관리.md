> 구현 확인 기준과 검증 범위는 [회원 전체 흐름](./0.회원%20전체%20흐름.md)을 따른다. 이 문서의 API는 Account 기준이며 Front 응답은 별도 표시한다.

# 📝 1.1.1 회원가입

## 기능 목적

> 유효한 조직 초대를 받은 비인증 사용자가 일반 회원으로 가입한다.

## 사용자 및 권한

- 인증 없이 요청할 수 있다.

## 사전 조건

- 사용할 수 있는 조직 초대 토큰이 있어야 한다.

## 입력값

API: `POST /api/accounts`

DTO: `CreateAccountRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `inviteToken` | UUID | O | null 불가, 사용할 수 있는 조직 초대 토큰 |
| `name` | String | O | 공백 불가, 최대 100자 |
| `email` | String | O | 공백 불가, 이메일 형식, 최대 254자 |
| `password` | String | O | 공백 불가, 6~64자 |

## 처리 절차

1. DTO를 검증하고 이메일을 앞뒤 공백 제거·소문자 변환한다.
2. BCrypt 비밀번호 해시와 외부 UUID를 준비하고 이메일 중복을 확인한다.
3. Inventory `POST /api/core/internal/invitations/use`에 토큰·이메일·계정 UUID를 전달한다.
4. 초대 사용 처리가 성공하면 `USER`, `ACTIVE` 계정을 `saveAndFlush()`로 저장한다.
5. Account 저장이 실패하면 Inventory 가입 보상을 요청한다. DB의 `uk_account_email` 위반이 확인된 경우 `A002`로 변환한다.

## 업무 규칙

- 초대 검증과 조직원 생성은 Inventory가 담당한다.
- Front는 비밀번호 확인용 `confirmPassword`도 검증하지만 Account로 전달하는 가입 DTO에는 포함하지 않는다.
- 사전 이메일 확인은 이메일을 예약하지 않는다. 최종 중복은 DB 고유 제약으로도 검증한다.
- Account와 Inventory는 단일 DB 트랜잭션이 아니다. 보상 요청 실패는 로그에 남으며 자동 복구 성공을 보장하지 않는다.

## 처리 결과

- `USER`, `ACTIVE` 계정이 생성된다.
- Account는 `201 Created`, `ApiResponse<Void>` (`data: null`)를 반환한다. 생성된 계정 객체를 반환하지 않는다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 입력 검증 실패 | `400 G001` |
| 이메일 중복 | `409 A002` |
| 유효하지 않은 초대 또는 이메일 불일치 | Inventory 검증에서 거부한다. Account는 연동 오류를 `502 G004`로 변환한다. |

# 📝 1.1.2 이메일 중복 확인

## 기능 목적

> 이메일의 사용 가능 여부를 확인한다.

## 사용자 및 권한

- 인증 없이 요청할 수 있다.

## 사전 조건

- 가입 여부와 관계없이 이메일의 사용 가능 여부를 확인할 수 있다.

## 입력값

API: `POST /api/accounts/check-email`

DTO: `EmailAvailabilityRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `email` | String | O | 공백 불가·이메일 형식·최대 254자 |

## 처리 절차

1. 이메일을 정규화한다.

## 업무 규칙

## 처리 결과

- Account는 `200 OK`, `ApiResponse<EmailAvailabilityResponse>`를 반환한다. `data.available: true`는 사용 가능, `false`는 사용 중이다.

# 📝 1.1.3 새 비밀번호 사용 가능 여부 확인

## 기능 목적

> 새 비밀번호가 현재 비밀번호와 다른지 확인한다.

## 사용자 및 권한

- 인증된 사용자. JWT UUID로 본인을 식별한다.

## 사전 조건

- JWT UUID에 해당하는 계정이 존재해야 한다.

## 입력값

API: `POST /api/accounts/check-pwd`

DTO: `PasswordReuseCheckRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `newPassword` | String | O | 공백 불가·6~64자 |

## 처리 절차

1. JWT UUID로 계정을 조회한다.
2. 입력값과 저장된 비밀번호 해시를 비교한다.

## 업무 규칙

- 이 API는 비밀번호를 변경하지 않는다.
- 같은 비밀번호일 때 `available: false`를 반환하지 않는다.
- 사용 가능 여부 확인 자체에는 `ACTIVE` 상태 검사가 없다. 실제 본인 비밀번호 변경 API에서는 `ACTIVE` 상태와 동일 비밀번호 여부를 검사한다.

## 처리 결과

- 기존 비밀번호와 다르면 사용 가능한 것으로 응답한다.
- Account는 `200 OK`, `ApiResponse<PasswordReuseCheckResponse>`의 `data.available: true`를 반환한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 현재와 동일한 비밀번호 | `400 A007` |
| 계정 없음 | `404 A001` |
| 입력 오류 | `400 G001` |

> 로그인한 본인의 계정 정보를 조회한다.

## 사용자 및 권한

- 인증된 사용자.

## 사전 조건

- JWT UUID에 해당하는 계정이 존재해야 한다.

## 입력값

API: `GET /api/accounts/me`

DTO: 없음.

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| 없음 | - | - | 별도 Path·Query·Body 없이 JWT Subject로 본인을 식별한다. |

# 📝 1.1.6 계정 탈퇴

## 기능 목적

> 현재 비밀번호를 확인하고 본인의 계정을 탈퇴 처리한다.

## 사용자 및 권한

- 인증된 사용자. JWT UUID로 본인을 식별한다.

## 사전 조건

- 외부 API에는 유효한 인증 정보와 본인의 현재 비밀번호가 필요하다.

## 입력값

API: `DELETE /api/accounts/me`

DTO: `WithdrawAccountRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `password` | String | O | 현재 비밀번호, 공백 불가·6~64자 |

## 처리 절차

1. 계정 조회 후 입력한 현재 비밀번호를 확인한다.
2. `accountUuid`, `previousEmail`로 Inventory `POST /api/core/internal/leave-org`를 호출한다.
3. Inventory는 조직원이 존재하면 관련 삭제 처리를 수행한다. 조직원이 이미 없으면 성공한다. 조직 `BOSS`는 탈퇴를 거부한다.
4. Account를 `WITHDRAWN`으로 바꾸고 `withdrawnAt`을 기록한다. 이메일과 비밀번호 해시를 null로 바꾼다.
5. Front의 탈퇴 요청에서는 현재 Refresh Token 폐기를 시도하고 두 인증 쿠키를 삭제한다.

## 업무 규칙

- 이름·UUID·내부 ID는 DB에 유지된다. 외부 회원 응답에서는 탈퇴자의 이름·이메일을 숨긴다.
- 엔티티는 `ACTIVE`, `LOCKED`, `INACTIVE`에서 탈퇴할 수 있지만 외부 API에는 유효한 인증 정보가 필요하다. 잠긴 계정용 별도 비인증 탈퇴 수단은 확인되지 않았다.
- Account 탈퇴 코드에는 모든 세션 토큰 폐기나 Access Token 즉시 차단이 없다. Inventory의 선행 변경과 Account 변경에 분산 원자성을 보장하지 않는다.

## 처리 결과

- 계정이 `WITHDRAWN`으로 변경되고 이메일·비밀번호 해시가 제거된다.
- Account 성공: `200 OK`, `ApiResponse<Void>`.
- Front `DELETE /withdraw` 성공: 현재 세션을 종료하고 `204 No Content`를 반환한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 입력 오류 | `400 G001` |
| 계정 없음 | `404 A001` |
| 비밀번호 불일치 | `400 A008` |
| 조직 탈퇴 실패 | `502 G004`. Account 탈퇴로 진행하지 않는다. |
| 이미 `WITHDRAWN`인 계정 | 엔티티는 `409 A006`으로 거부한다. 외부 탈퇴 API는 먼저 비밀번호를 검증하므로 동일 오류가 항상 우선 반환되는 것은 아니다. |

# 📝 1.1.8 로그인

## 기능 목적

> 이메일과 비밀번호를 확인하고 인증 토큰을 발급한다.

## 사용자 및 권한

- 인증 없이 요청할 수 있다.

## 사전 조건

- 등록된 이메일과 일치하는 비밀번호가 필요하다.
- 계정 상태가 `ACTIVE` 또는 `INACTIVE`여야 토큰을 발급할 수 있다.

## 입력값

API: `POST /api/auth/login`

DTO: `LoginRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `email` | String | O | 공백 불가·이메일 형식·최대 254자 |
| `password` | String | O | 공백 불가·6~64자 |

## 처리 절차

1. 이메일을 정규화하고 비밀번호를 확인한다.
2. 계정 상태를 확인하고 Access Token과 Refresh Token을 발급한다.

## 업무 규칙

- `INACTIVE`는 토큰 발급이 가능하다. Front는 `account_status` claim을 읽고 일반 화면 접근 시 `/reactivation`으로 이동시킨다.
- 탈퇴 시 이메일·비밀번호 해시가 삭제되므로 기존 이메일로 다시 로그인할 때는 계정을 찾지 못해 `AU001`이 반환될 수 있다.

## 처리 결과

- Access Token과 Refresh Token이 발급된다.
- Account는 `200 OK`, `ApiResponse<LoginResponse>`의 `accessToken`, `refreshToken`을 반환한다. 응답 헤더는 `Cache-Control: no-store`다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 입력 오류 | `400 G001` |
| 인증 정보 불일치 | `401 AU001` |
| 검증된 계정이 `LOCKED` | `403 A004` |
| 검증된 계정이 `WITHDRAWN` | `403 A005` |

# 📝 1.1.9 인증 갱신

## 기능 목적

> Refresh Token을 소비하고 새 인증 토큰을 발급한다.

## 사용자 및 권한

- Access Token 인증 없이 Refresh Token으로 요청할 수 있다.

## 사전 조건

- 만료되지 않았고 아직 소비되지 않은 Refresh Token이 있어야 한다.
- 토큰에 연결된 계정이 존재하고 상태가 `ACTIVE` 또는 `INACTIVE`여야 한다.

## 입력값

API: `POST /api/auth/refresh`

DTO: `RefreshTokenRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `refreshToken` | String | O | 공백 불가·최대 128자, `32자리 소문자 hex.64자리 소문자 hex` 형식 |

## 처리 절차

1. SHA-256 기반 Redis 키를 `getAndDelete()`하여 기존 토큰을 한 번만 소비한다.
2. 해당 계정을 조회하고 토큰 발급 가능 상태인지 확인한다.
3. 새 Access Token과 Refresh Token을 반환한다. Front는 두 쿠키를 교체한다.

## 업무 규칙

- 소비 이후 계정 확인이나 발급에 실패해도 기존 토큰이 복원되지는 않는다.

## 처리 결과

- 기존 Refresh Token이 소비되고 새 Access Token과 Refresh Token이 발급된다.
- Account는 `200 OK`, `ApiResponse<LoginResponse>`를 반환한다. 응답 헤더는 `Cache-Control: no-store`다.
- Front `POST /refresh`는 두 인증 쿠키를 교체하고 `204 No Content`를 반환한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 입력 형식 오류 | `400 G001` |
| 만료·재사용·미등록 토큰 또는 계정 소실 | `401 AU003` |
| 연결된 계정이 `LOCKED` | `403 A004` |
| 연결된 계정이 `WITHDRAWN` | `403 A005` |
| Front에서 갱신할 쿠키가 없거나 갱신 실패 | Front는 `401 Unauthorized`를 반환한다. |

# 📝 1.1.10 로그아웃

## 기능 목적

> 제출한 Refresh Token을 폐기하고 Front의 인증 쿠키를 삭제한다.

## 사용자 및 권한

- Access Token 인증 없이 Refresh Token으로 요청할 수 있다.

## 사전 조건

- Account API에는 형식에 맞는 Refresh Token을 제출해야 한다.
- Front는 Refresh Token 쿠키가 없어도 인증 쿠키를 삭제하고 로그아웃을 완료한다.

## 입력값

API: `POST /api/auth/logout`

DTO: `RefreshTokenRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `refreshToken` | String | O | 공백 불가·최대 128자, `32자리 소문자 hex.64자리 소문자 hex` 형식 |

## 처리 절차

1. Front `POST /logout`은 현재 쿠키의 Refresh Token을 읽는다.
2. 토큰이 있으면 Account `POST /api/auth/logout`을 호출한다.
3. Account는 제출한 토큰의 Redis 키를 삭제한다.
4. Front는 Account 호출 성공 여부와 관계없이 두 인증 쿠키를 삭제하고 `/`로 이동한다.

## 업무 규칙

- 올바른 형식의 토큰이 이미 없더라도 삭제는 성공으로 처리한다.
- 쿠키 삭제만으로 이미 발급한 Access Token이 서버에서 즉시 무효화되는 것은 아니다.

## 처리 결과

- Account에서 삭제가 완료된 Refresh Token은 갱신에 사용할 수 없다.
- Account는 `204 No Content`를 반환한다. Front는 인증 쿠키를 삭제하고 `/`로 이동한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| Account 요청의 입력 형식 오류 | `400 G001` |
| Front에서 Refresh Token 폐기 외부 호출 실패 | 쿠키를 삭제하고 `/`로 이동한다. |
