# 📝 1.0 회원 전체 흐름

> 2026-09-17 로컬 체크아웃의 소스와 설정을 확인한 명세다. 이번 문서 수정에서는 테스트·브라우저·운영 환경 검증을 수행하지 않았다.

## 현재 구현 구조

| 구성 요소 | 회원 기능에서의 역할 |
| --- | --- |
| Account | 계정 생성·조회·변경·탈퇴, 권한·상태 확인, 인증 토큰 발급, 비밀번호 재설정·재활성화 처리 |
| Front | 회원 화면과 폼 검증, Account API 호출, 인증 쿠키 저장·교체·삭제, 처리 결과 안내 |
| Inventory | 회원가입 시 조직 초대 검증·조직원 생성, 회원 탈퇴 시 조직 탈퇴 처리 |
| Redis | Refresh Token과 이메일 링크 토큰 저장·소비, 복구 메일 발급 간격 제한 |

## 용어

| 용어 | 의미 |
| --- | --- |
| `accountId` | DB 내부 Long 식별자. 외부 회원 응답에는 포함하지 않는다. |
| `uuid` | 외부 계정 식별자이자 JWT `sub` |
| `email` | 로그인·이메일 인증에 사용하는 주소. 서비스에서 `trim()` 후 `Locale.ROOT` 기준 소문자로 정규화한다. |
| `inviteToken` | 일반 회원가입에 필요한 UUID 형식의 조직 초대 토큰 |
| Access Token | Account가 RS256으로 서명한 JWT. UUID·권한·발급 시점의 계정 상태 등을 포함한다. |
| Refresh Token | 새 Access Token과 Refresh Token 발급에 사용하는 무작위 문자열 |
| 복구 토큰 | 비밀번호 재설정 또는 재활성화용 이메일 링크의 64자리 16진수 문자열 |

## 처리 순서

| 상황 | 처리 흐름 | 완료 결과 |
| --- | --- | --- |
| 신규 사용자 | 초대 링크 검증 → 이메일 중복 확인 → 초대 토큰과 가입 정보 제출 | Inventory 초대 사용·조직원 생성 후 `USER`, `ACTIVE` 계정 저장 |
| 로그인 | 이메일·비밀번호 확인 → 상태 확인 | `ACTIVE`와 `INACTIVE`에 두 토큰 발급. Front는 `INACTIVE`를 재활성화 화면으로 안내 |
| 인증 연장 | 기존 Refresh Token 소비 → 계정 상태 확인 → 두 토큰 재발급 | 기존 Refresh Token 재사용 불가, Front의 두 쿠키 교체 |
| 이름 변경 | JWT UUID로 본인 확인 → `ACTIVE` 확인 → 이름 저장 | 이름과 수정 일시 갱신 |
| 비밀번호 변경 | 현재 비밀번호 확인 → 새 비밀번호 재사용 확인 → BCrypt 저장 | 비밀번호 변경. 전체 Refresh Token 폐기는 연결되어 있지 않음 |
| 비밀번호 분실 | 이메일 제출 → 링크 수신 → 새 비밀번호 제출 | 유효한 토큰을 소비하고 `ACTIVE` 계정의 비밀번호 변경 |
| 비활성 계정 사용 | 로그인 → 재활성화 메일 요청 → 동일 계정으로 링크 토큰 확인 | `INACTIVE` → `ACTIVE`, Front에서 현재 세션 종료 후 다시 로그인 |
| 잠긴 계정 | 활성 관리자에게 잠금 해제 요청 | `LOCKED` → `ACTIVE` |
| 탈퇴 | 현재 비밀번호 확인 → Inventory 조직 탈퇴 → Account 탈퇴 | `WITHDRAWN`, 이메일·비밀번호 해시 제거. Front는 현재 세션 종료 |
| 로그아웃 | Front에서 현재 Refresh Token 폐기 요청 → Account에서 토큰 삭제 → Front 쿠키 삭제 | 폐기에 성공한 Refresh Token으로 갱신 불가. Front는 폐기 호출 실패 시에도 쿠키 삭제 |

## 계정 필드와 입력 제약

API 입력 제약과 DB 컬럼 정의를 구분한다.

| 필드 | 타입 | 입력·저장 규칙 |
| --- | --- | --- |
| `accountId` | Long | DB 자동 생성 |
| `uuid` | UUID | 생성 시 발급, 변경 불가·고유 |
| `name` | String | 가입·이름 변경 DTO에서 공백 불가, 최대 100자. DB 컬럼은 255자·NOT NULL |
| `email` | String | DTO에서 공백 불가·이메일 형식·최대 254자. DB는 255자·고유·null 허용 |
| `hashedPassword` | String | 요청 비밀번호는 공백 불가·6~64자. BCrypt 해시를 DB의 256자 컬럼에 저장 |
| `accountRole` | Enum | `USER`, `ADMIN`. 일반 초대 가입은 `USER`, 관리자 생성 API는 `ADMIN` |
| `accountStatus` | Enum | `ACTIVE`, `LOCKED`, `INACTIVE`, `WITHDRAWN`. 생성 시 `ACTIVE` |
| `createdAt` | LocalDateTime | 최초 저장 시 기록 |
| `updatedAt` | LocalDateTime | 최초 저장·엔티티 갱신 시 기록 |
| `withdrawnAt` | LocalDateTime | 탈퇴 전 null, 탈퇴 시 기록 |

이름과 비밀번호 수정 DTO는 분리되어 있다. `UpdateAccountNameRequest`는 `name`만, `ChangeOwnPasswordRequest`는 `currentPassword`, `newPassword`를 받는다. 일반 가입에는 `inviteToken`이 추가로 필요하며 Front의 `confirmPassword`는 Account 가입 DTO에 포함되지 않는다.

탈퇴 시 DB의 이름·UUID·내부 ID는 유지된다. 외부 `AccountResponse`는 탈퇴 계정의 이름과 이메일을 null로 가린다.

## 공통 원칙

### 문서 구성과 응답 표기

- 기능은 기능 목적 → 사용자 및 권한 → 사전 조건 → 입력값 → 처리 절차 → 업무 규칙 → 처리 결과 → 예외 처리 순서로 작성한다. 권한·상태 정의는 정의표와 전이 규칙으로 정리한다.
- 입력값은 `항목 / 형식 / 필수 여부 / 설명`, 예외 처리는 `예외 조건 / 처리` 표를 사용한다. 입력이 없으면 없음으로 표시한다.
- API·DTO·HTTP 상태·오류 코드는 Account 기준이다. Front 화면 경로와 응답은 `Front`를 붙여 구분한다. 상세 요청·응답 예시는 회원 API 명세를 따른다.
- 인증이 필요한 API에서 Access Token이 없거나 유효하지 않으면 `401 AU002`를 반환한다. 관리자 API는 JWT 권한과 DB의 활성 관리자 여부를 추가로 확인한다.
- DTO 검증 실패는 `400 G001`이다. 각 기능의 예외 표에는 기능별 주요 실패 조건을 기재한다.

### 인증과 토큰

| 구분 | 현재 구현 | 기본 만료 |
| --- | --- | --- |
| Access Token | RS256, `sub`, `roles`, `account_status`, `iss`, `aud`, `iat`, `exp`, 헤더 `kid` | 30분 (`JWT_ACCESS_TOKEN_TTL`) |
| Refresh Token | `32자리 hex.64자리 hex`, Redis 키는 토큰의 SHA-256 해시, 값은 계정 UUID | 14일 (`REFRESH_TOKEN_TTL`) |
| 비밀번호 재설정 | Redis에 링크 토큰과 이메일 연결, 토큰 원문이 키·이메일 인덱스에 포함됨 | 5분, 이메일별 발급 간격 1분 |
| 재활성화 | Redis에 링크 토큰과 계정 UUID 연결, 소유 계정 확인 후 Lua로 소비 | 10분, 계정별 발급 간격 30초 |

- JWT 기본 발급자는 `account-api`, 발급 audience는 `account-api`, `inventory-api`, `rule-engine`이다.
- Front는 `access_token`, `refresh_token`을 `HttpOnly`, `SameSite=Lax`, `Path=/` 쿠키로 저장한다. `Secure`는 `cookie.secure` 설정을 따른다.
- Account API는 Bearer 인증을 사용한다. 브라우저 쿠키와 Front 화면 URL을 Account API DTO·URL과 구분한다.
- JWT의 상태는 발급 당시 값이다. 로그아웃·비밀번호 변경·상태 변경·탈퇴가 이미 발급한 Access Token을 즉시 무효화하는 공통 차단 기능은 확인되지 않았다.
- 비밀번호 변경·재설정·탈퇴 시 해당 계정의 모든 Refresh Token을 일괄 폐기하는 호출은 없다. 갱신 시에는 DB에서 계정 상태를 다시 확인한다.
- Redis 토큰 소비와 DB 변경은 하나의 원자적 트랜잭션이 아니다. DB 처리 실패 시 이미 소비한 토큰이 자동 복구된다고 보장하지 않는다.
