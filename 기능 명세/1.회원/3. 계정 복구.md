# 📝 1.3 계정 복구

> [회원 전체 흐름](./0.회원%20전체%20흐름.md)의 소스 확인 기준을 따른다. 현재 복구는 이메일 링크의 일회용 토큰을 사용한다. 숫자 코드 입력이나 `LINK`·`CODE` 방식 선택 API는 없다.

## 공통 원칙

| 구분 | 비밀번호 재설정 | 비활성 계정 재활성화 |
| --- | --- | --- |
| 요청 인증 | 인증 불필요 | 로그인한 계정의 JWT 필요 |
| 식별 정보 | 입력 이메일 | JWT 계정 UUID |
| 링크 | `/pwd/{token}` | `/reactivation?token={token}` |
| 토큰 형식 | 32바이트 난수 → 64자리 hex | 32바이트 난수 → 64자리 hex |
| 유효시간 | 5분 | 10분 |
| 발급 간격 | 이메일별 1분 | 계정별 30초 |
| 소비 | Redis `getAndDelete()` | Redis Lua로 소유 UUID 확인 후 삭제 |
| 기존 토큰 | 새 발급 시 같은 이메일의 이전 토큰 삭제 | 새 발급 시 같은 계정의 이전 토큰 삭제 |

- 복구 토큰은 Redis 키와 이메일·계정별 인덱스에 원문으로 포함된다. Refresh Token의 SHA-256 저장 방식과 다르다.
- 발급 간격 제한은 구현되어 있으나 IP별 요청 제한·인증 실패 횟수 제한은 확인되지 않았다.

# 📝 1.3.1 비밀번호 재설정 요청

## 기능 목적

> 입력한 이메일로 비밀번호 재설정 링크를 요청한다.

## 사용자 및 권한

- 인증 없이 요청할 수 있다.

## 사전 조건

- 메일을 발급하려면 입력 이메일에 해당하는 계정이 존재해야 한다.
- 미등록 이메일도 요청할 수 있으며, 같은 접수 응답을 반환한다.

## 입력값

API: `POST /api/accounts/pwd`

Front 화면: `/forgot-password`

DTO: `ResetPasswordTokenRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `email` | String | O | 공백 불가·이메일 형식·최대 254자 |

## 처리 절차

1. 이메일을 정규화하고 계정 존재 여부를 확인한다.
2. 계정이 없으면 메일을 발송하지 않고 종료한다.
3. Redis에서 이메일별 발급 간격을 확인한다. 1분 이내 재요청이면 추가 발급 없이 종료한다.
4. 기존 토큰을 지우고 5분 유효 토큰을 발급한다.
5. 설정된 Front 주소와 `/pwd/{token}`으로 만든 링크를 메일 발송 이벤트에 전달한다.

## 업무 규칙

- 토큰 요청 단계는 계정의 `ACTIVE` 여부를 확인하지 않는다. 실제 비밀번호 저장 단계에서는 `ACTIVE`만 허용한다.
- `202`는 요청 처리 결과이며 SMTP 발송 완료나 사용자 수신 확인을 뜻하지 않는다.

## 처리 결과

- 정상 접수·미등록 이메일·발급 간격 내 재요청은 동일하게 `202 Accepted`, `ApiResponse<Void>`를 반환한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| DTO 입력 오류 | `400 G001` |
| 토큰 발급·이벤트 발행 중 오류 | 발급 간격 제한 해제를 시도한 뒤 예외를 전달한다. 항상 `202 Accepted`를 반환하지는 않는다. |

# 📝 1.3.2 재설정 링크 열기

## 기능 목적

> 이메일 링크를 통해 새 비밀번호 입력 폼을 연다.

## 사용자 및 권한

- 인증 없이 요청할 수 있다.

## 사전 조건

- 요청 경로에 이메일 링크의 `token` 값이 있어야 한다.

## 입력값

Front 화면: `GET /pwd/{token}`

DTO: 없음. Path의 토큰을 입력 폼에 전달한다.

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `token` | String, Path | O | 이메일 링크의 토큰 |

## 처리 절차

1. 사용자가 Front `GET /pwd/{token}`에 접근한다.
2. 새 비밀번호 입력 폼을 보여 준다.

## 업무 규칙

- 링크를 여는 단계에서는 토큰의 유효성을 검증하거나 소비하지 않는다.
- 별도의 인증 코드 확인 API나 코드 확인 후 두 번째 토큰을 발급하는 단계는 없다.

## 처리 결과

- 새 비밀번호 입력 폼을 표시한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 만료·사용 완료된 토큰으로 링크 접근 | 이 단계에서는 입력 폼을 표시한다. 토큰 유효성은 새 비밀번호 설정 요청에서 검사한다. |

# 📝 1.3.3 새 비밀번호 설정

## 기능 목적

> 이메일 링크 토큰을 소비하고 새 비밀번호를 저장한다.

## 사용자 및 권한

- 인증 없이 요청할 수 있다.

## 사전 조건

- 비밀번호를 변경할 계정이 `ACTIVE`여야 한다.
- 만료되지 않았고 아직 소비되지 않은 비밀번호 재설정 토큰이 있어야 한다.

## 입력값

API: `POST /api/accounts/pwd/reset/{token}`

DTO: `ResetPasswordRequest`

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| `token` | String, Path | O | 발급받은 링크 토큰 |
| `password` | String, Body | O | 공백 불가·6~64자 |

## 처리 절차

1. Front 폼은 새 비밀번호와 확인 비밀번호의 일치를 검증한다. Account에는 `ResetPasswordRequest.password`만 전달한다.
2. Account는 요청 DTO를 검증한 뒤 Redis에서 토큰을 조회하면서 삭제한다.
3. 연결된 이메일로 계정을 조회한다.
4. 계정이 `ACTIVE`인지 확인하고 새 비밀번호를 BCrypt로 저장한다.

## 업무 규칙

- `LOCKED`·`INACTIVE` 상태는 이 기능으로 해제되지 않는다.
- 현재 이 경로에서는 기존 비밀번호와의 동일 여부를 검사하지 않으며, 전체 Refresh Token 폐기와 비밀번호 변경 완료 메일 발송도 연결되어 있지 않다.
- 토큰을 먼저 소비하므로 이후 DB 처리에 실패하면 새 링크를 요청해야 한다. Redis와 DB를 한 트랜잭션으로 롤백한다고 보장하지 않는다.

## 처리 결과

- 새 비밀번호의 BCrypt 해시가 저장된다.
- Account는 `200 OK`, `ApiResponse<Void>`를 반환한다. Front는 성공 후 로그인 화면으로 이동한다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| Front 폼의 비밀번호·확인 비밀번호 불일치 | Account를 호출하지 않고 비밀번호 입력 폼을 다시 표시한다. |
| Account 요청의 비밀번호 입력 오류 | `400 G001`. 요청 DTO 검증에 실패하면 토큰을 소비하지 않는다. |
| 토큰 없음·만료·사용 완료 | `400 A009` |
| 계정 없음 | `404 A001` |
| 계정 상태가 `ACTIVE`가 아님 | `409 A006` |

# 📝 1.3.4 비활성 계정 재활성화

## 기능 목적

> 로그인한 비활성 계정의 이메일 링크를 확인하고 계정을 활성화한다.

## 사용자 및 권한

- 인증된 사용자. JWT UUID로 본인을 식별한다.

## 사전 조건

- 계정 상태가 `INACTIVE`여야 한다. `INACTIVE` 계정은 로그인해 토큰을 발급받을 수 있다.
- 확인 단계에서는 로그인한 계정에 발급된 유효한 링크 토큰이 필요하다.

## 입력값

| 단계 | API |
| --- | --- |
| 메일 요청 | `POST /api/accounts/me/reactivation/verification` |
| 확인 | `POST /api/accounts/me/reactivation/confirm` |

DTO: 메일 요청은 없음, 확인은 `ReactivationConfirmRequest`.

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| 메일 요청 | - | - | Body 없음 |
| `token` | String, Body | O (확인) | 공백 불가, `^[0-9a-f]{64}$` |

이메일·UUID를 body에서 입력받지 않는다.

## 처리 절차

1. 메일 요청 시 요청 계정이 존재하고 `INACTIVE`인지 확인한다. 다른 상태면 `409 A006`이다.
2. 계정별 30초 발급 간격을 확인하고 10분 유효 링크 토큰을 이메일 발송 이벤트로 전달한다. 제한 시간 내 재요청도 `202`로 응답한다.
3. 로그인한 사용자가 링크의 토큰을 제출한다.
4. Redis Lua 스크립트가 토큰의 소유 UUID와 요청자의 UUID가 같을 때만 토큰 키를 삭제한다.
5. DB의 계정이 여전히 `INACTIVE`이면 `ACTIVE`로 변경한다.
6. Front는 현재 Refresh Token 폐기를 시도하고 인증 쿠키를 삭제한 뒤 다시 로그인하도록 안내한다.

## 업무 규칙

- 소유자가 다른 사용자의 요청은 정상 소유자의 토큰을 소비하지 않는다.
- 소유자 확인과 토큰 키 삭제만 Redis Lua 안에서 원자적으로 수행한다. DB 상태 변경까지 포함한 원자성은 아니다.
- `LOCKED`·`WITHDRAWN`은 이 경로로 복구할 수 없다.

## 처리 결과

| 단계 | 처리 결과 |
| --- | --- |
| 메일 요청 | Account는 `202 Accepted`, `ApiResponse<Void>`로 접수 결과를 반환한다. |
| 확인 | 계정이 `ACTIVE`로 변경된다. Account는 `200 OK`, `ApiResponse<AccountResponse>`를 반환하고 Front는 현재 세션을 종료한 뒤 로그인 화면으로 이동한다. |

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 인증 없음·유효하지 않은 JWT | `401 AU002` |
| 계정 없음 | `404 A001` |
| 메일 요청 시 계정이 `INACTIVE`가 아님 | `409 A006` |
| 토큰 형식 오류 | `400 G001` |
| 소유자 불일치·만료·이미 사용된 토큰 | `400 A009` |
| 메일 요청과 확인 사이에 상태가 바뀜 | 토큰 소비 후 `409 A006`이 발생할 수 있다. |
| 토큰 발급·이벤트 발행 중 오류 | 발급 간격 제한 해제를 시도한 뒤 예외를 전달한다. |
