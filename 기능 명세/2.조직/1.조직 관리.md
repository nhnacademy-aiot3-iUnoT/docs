# 📝 2.1.1 조직 생성 초대 (Admin)

## 기능 목적

> 서비스 관리자가 새로운 조직 생성을 위한 초대 링크를 발급한다.

## 권한
- Role : `ADMIN`

## 처리 절차
1. 관리자가 조직 생성 초대를 요청한다.
2. 시스템은 조직 생성용 초대 토큰을 생성한다.
3. 초대 토큰의 만료 시간을 설정한다.
4. 조직 생성 초대 링크를 생성한다.
5. 생성된 초대 링크를 관리자에게 제공한다.

## 업무 규칙

- ADMIN만 발급할 수 있다.
- 초대 링크는 1회만 사용할 수 있다.
- 만료 시간이 지나면 사용할 수 없다.


## 처리 결과

- [ ] 조직 생성 초대 링크가 생성된다.

# 📝 2.1.2 조직 생성

## 기능 목적

> 서비스 관리자가 발급한 조직 생성 초대 링크를 통해 기관 담당자(Owner)가 회원가입을 완료하고 새로운 조직을 생성한다.

## 사전 조건

- 유효한 조직 생성 초대 토큰이어야 한다.
- 초대 토큰이 만료되지 않아야 한다.
- 초대 토큰이 사용되지 않은 상태여야 한다.

## 입력값

| 항목 | 형식 | 필수 | 설명 |
|------|------|:---:|------|
| 이름 | String | O | Owner 이름 |
| 이메일 | String | O | 로그인 계정 |
| 비밀번호 | String | O | 비밀번호 |
| 기관명 | String | O | 2~30자 |
| 주소 | String | O | 도로명 주소 |
| 기관 설명 | String | X | 기관 설명 |

## 처리 절차

1. 사용자가 조직 생성 초대 링크로 접속한다.
2. 시스템은 초대 토큰의 유효성을 검증한다.
3. 사용자는 회원가입 정보와 기관 정보를 입력한다.
4. 시스템은 이메일 및 기관명+주소의 중복 여부를 확인한다.
5. Account를 생성한다.
6. Organization을 생성한다.
7. OrganizationMember를 생성하고 조직 역할(Role)을 `OWNER`로 설정한다.
8. 초대 토큰을 사용 완료 상태로 변경한다.

## 업무 규칙

- 조직 생성은 조직 생성 초대 링크를 통해서만 가능하다.
- 기관명과 주소는 필수 입력값이다.
- 기관명과 주소의 조합은 중복될 수 없다.
- 이메일은 시스템 내에서 중복될 수 없다.
- 최초 생성자는 조직 역할(Role)이 `OWNER`로 설정된다.
- 초대 토큰은 한 번만 사용할 수 있다.

## 처리 결과

- [ ] Account가 생성된다.
- [ ] 새로운 Organization이 생성된다.
- [ ] 생성자는 `OWNER` 역할을 가진 OrganizationMember가 된다.
- [ ] 초대 토큰이 사용 완료 상태로 변경된다.

## 예외 처리

| 예외 조건 | 처리 |
|-----------|------|
| 초대 토큰이 만료됨 | 만료된 초대 링크임을 반환한다. |
| 이미 사용된 초대 토큰 | 사용할 수 없는 초대 링크임을 반환한다. |
| 이메일이 이미 존재함 | 이미 가입된 이메일임을 반환한다. |
| 기관명 + 주소가 이미 존재함 | 이미 등록된 조직임을 반환한다. |

# 📝 2.1.2 조직 조회

# 📝 2.1.3 조직 수정

## 기능 목적

> 조직 정보를 수정한다.

## 사용자 및 권한

- Role : `OWNER`

## 입력값

| 항목       | 형식      | 필수 여부 | 설명            |
|----------|---------|:-----:|---------------|
| 조직명      | String  |   O   | 2~30자   |
| 주소       | String  |   O   | (도로명 주소, 우편 번호) |
| 조직 설명    | String  |   X   | 조직에 대한 설명     |

## 처리 절차

1. 사용자 Role을 확인한다. (Owner)
2. 조직 상태를 확인한다. (ACTIVE)
3. 입력값을 검증한다.
4. 조직 정보를 수정한다.

## 업무 규칙

- `OWNER`만 조직 정보를 수정할 수 있다.
- 조직명과 주소는 필수 입력값이다.
- 조직명 + 주소는 시스템 내에서 중복될 수 없다.
- 조직명은 2~30자까지 입력할 수 있다.

## 처리 결과

- [ ] 조직 정보가 수정된다.

## 예외 처리

| 예외 조건               | 처리                      |
|---------------------|-------------------------|
| `OWNER`가 아님         | 수정 권한이 없음을 반환한다.        |
| 조직 상태가 `ACTIVE`가 아님 | 수정을 거부한다.               |
| 조직이 중복임             | 존재하는 조직임을 반환한다. (문자 출력) |

# 📝 2.1.4 조직 상태 변경

## 기능 목적

> 조직의 운영 상태를 `ACTIVE` 또는 `INACTIVE`로 변경한다.

## 사용자 및 권한

- Role : `OWNER`

## 사전 조건

- 조직이 존재해야 한다.
- 조직 상태가 `CLOSED`가 아니어야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| 조직 상태 | Enum | O | `ACTIVE` 또는 `INACTIVE` |

## 처리 절차

1. Owner 권한을 가진 사용자가 로그인한다.
2. 시스템은 조직 존재 여부를 확인한다. 
3. Owner는 조직 상태를 변경한다. 
4. 조직 상태는 ACTIVE와 INACTIVE 사이에서 변경할 수 있다. 
5. 변경된 조직 상태는 시스템에 저장된다.

## 업무 규칙

- `OWNER`만 수행할 수 있다.
- `ACTIVE` → `INACTIVE`로 변경할 수 있다.
- `INACTIVE` → `ACTIVE`로 변경할 수 있다.
- `CLOSED` 상태의 조직은 상태를 변경할 수 없다.

## 처리 결과

- [ ] 조직 상태가 요청한 상태(`ACTIVE` 또는 `INACTIVE`)로 변경된다.

## 예외 처리

| 예외 조건               | 처리               |
|---------------------|------------------|
| `OWNER`가 아님         | 권한 없음을 반환한다.     |
| 존재하지 않는 조직          | 조직이 존재하지 않음을 반환한다. |
| 조직 상태가 `CLOSED`인 경우 | 상태 변경을 거부한다.     |

# 📝 2.1.5 조직 폐쇄

## 기능 목적

> 조직 운영을 종료한다.

## 사용자 및 권한

- Role : `OWNER`

## 사전 조건

- 조직이 존재해야 한다.

## 처리 절차

1. Owner 권한 확인
2. 조직 상태 확인
3. CLOSED 변경
4. OrganizationMember 상태 REMOVED
5. 초대 링크 모두 만료

## 업무 규칙

- `OWNER`만 수행할 수 있다.
- `CLOSED` 상태의 조직은 복구할 수 없다.

## 처리 결과

- [ ] 조직 상태가 `CLOSED`로 바뀐다.
- [ ] 조직원들과 조직의 관계가 `REMOVED` 바뀐다.

## 예외 처리

| 예외 조건          | 처리             |
|----------------|----------------|
| `OWNER`가 아님    | 권한 없음을 반환한다.   |
| 이미 `CLOSED` 상태 | 폐쇄된 조직임을 반환한다. |
