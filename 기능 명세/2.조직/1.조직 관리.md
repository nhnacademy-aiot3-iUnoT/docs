
# [ 조직 / 저장소 전체 사전 조건 ]
- 로그인한 사용자여야 한다.
- 회원 상태가 `ACTIVE`여야 한다.

# 📝 2.1.1 조직 생성

## 기능 목적

> 사용자가 새로운 조직을 생성하고 조직의 소유자자로 등록한다.

## 사전 조건

- 현재 `ACTIVE` 상태의 조직 소속이 없어야 한다.
- 진행 중(`PENDING`)인 조직 가입 요청이 없어야 한다.

## 입력값

| 항목    | 형식 | 필수 여부 | 설명              |
|-------| --- |:-----:|-----------------|
| 조직명   | String |   O   | 2~30자           |
| 주소    | String |   O   | (도로명 주소, 우편 번호) |
| 조직 설명 | String |   X   | 조직에 대한 설명       |

## 처리 절차
1. 사용자는 로그인에 성공하여 ACTIVE 상태여야 한다.
2. 사용자가 어떠한 조직에도 소속되어 있지 않고 가입 요청도 없는 경우 조직 생성이 가능하다.
3. 사용자는 조직 생성 화면에서 다음 정보를 입력한다 (조직명, 주소, 조직 설명)
4. 시스템은 입력 정보를 검증한 후 조직 정보를 저장한다.
5. 조직 생성자는 해당 조직의 OWNER 권한으로 등록되며, 조직 상태는 ACTIVE로 설정된다.

## 업무 규칙

- 조직명과 주소는 필수 입력값이다.
- 조직명 + 주소는 시스템 내에서 중복될 수 없다.
- 조직명은 2~30자까지 입력할 수 있다.
- 허용되지 않은 특수문자는 사용할 수 없다.
- 조직 생성자는 `OWNER` 역할을 가진다.
- 조직 생성 시 상태는 `ACTIVE`이다.

## 처리 결과

- [ ] 새로운 조직이 생성된다.
- [ ] 생성자는 `OWNER` 역할을 가진다.
- [ ] 조직 상태는 `ACTIVE`로 저장된다.

## 예외 처리

| 예외 조건            | 처리                                     |
|------------------|----------------------------------------|
| 이미 조직에 소속되어 있음   | 조직 생성을 거부한다. (메인 화면으로 이동)              |
| 진행 중인 가입 요청이 존재함 | 진행 중인 요청이 있음을 반환한다. (요청 내역 조회 화면으로 이동) |
| 조직이 존재함          | 조직이 중복됨을 반환한다. (메시지 출력)                |

## 기능 목적

# 📝 2.1.3 조직 수정

## 기능 목적

> 조직 정보를 수정한다.

## 사용자 및 권한

- Role : `OWNER`

## 입력값

| 항목       | 형식      | 필수 여부 | 설명            |
|----------|---------|:-----:|---------------|
| 조직명      | String  |   O   | 2~30자   |
| 주소       | String  |   O   | (도로명 주소, 우편 번호) |
| 조직 설명    | String  |   X   | 조직에 대한 설명     |

## 처리 절차

1. 사용자 Role을 확인한다. (Owner)
2. 조직 상태를 확인한다. (ACTIVE)
3. 입력값을 검증한다.
4. 조직 정보를 수정한다.

## 업무 규칙

- `OWNER`만 조직 정보를 수정할 수 있다.
- 조직명과 주소는 필수 입력값이다.
- 조직명 + 주소는 시스템 내에서 중복될 수 없다.
- 조직명은 2~30자까지 입력할 수 있다.

## 처리 결과

- [ ] 조직 정보가 수정된다.

## 예외 처리

| 예외 조건               | 처리                      |
|---------------------|-------------------------|
| `OWNER`가 아님         | 수정 권한이 없음을 반환한다.        |
| 조직 상태가 `ACTIVE`가 아님 | 수정을 거부한다.               |
| 조직이 중복임             | 존재하는 조직임을 반환한다. (문자 출력) |

# 📝 2.1.4 조직 상태 변경

## 기능 목적

> 조직의 운영 상태를 `ACTIVE` 또는 `INACTIVE`로 변경한다.

## 사용자 및 권한

- Role : `OWNER`

## 사전 조건

- 조직이 존재해야 한다.
- 조직 상태가 `CLOSED`가 아니어야 한다.

## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| 조직 상태 | Enum | O | `ACTIVE` 또는 `INACTIVE` |

## 처리 절차

1. Owner 권한을 가진 사용자가 로그인한다.
2. 시스템은 조직 존재 여부를 확인한다. 
3. Owner는 조직 상태를 변경한다. 
4. 조직 상태는 ACTIVE와 INACTIVE 사이에서 변경할 수 있다. 
5. 변경된 조직 상태는 시스템에 저장된다.

## 업무 규칙

- `OWNER`만 수행할 수 있다.
- `ACTIVE` → `INACTIVE`로 변경할 수 있다.
- `INACTIVE` → `ACTIVE`로 변경할 수 있다.
- `CLOSED` 상태의 조직은 상태를 변경할 수 없다.

## 처리 결과

- [ ] 조직 상태가 요청한 상태(`ACTIVE` 또는 `INACTIVE`)로 변경된다.

## 예외 처리

| 예외 조건               | 처리               |
|---------------------|------------------|
| `OWNER`가 아님         | 권한 없음을 반환한다.     |
| 존재하지 않는 조직          | 조직이 존재하지 않음을 반환한다. |
| 조직 상태가 `CLOSED`인 경우 | 상태 변경을 거부한다.     |

# 📝 2.1.5 조직 폐쇄

## 기능 목적

> 조직 운영을 종료한다.

## 사용자 및 권한

- Role : `OWNER`

## 사전 조건

- 조직이 존재해야 한다.

## 처리 절차

1. 사용자 권한을 확인한다.
2. 조직 상태를 `CLOSED`로 변경한다.
3. 모든 조직원의 소속 상태를 `REMOVED`로 변경한다.

## 업무 규칙

- `OWNER`만 수행할 수 있다.
- `CLOSED` 상태의 조직은 복구할 수 없다.

## 처리 결과

- [ ] 조직 상태가 `CLOSED`로 바뀐다.
- [ ] 조직원들과 조직의 관계가 `REMOVED` 바뀐다.

## 예외 처리

| 예외 조건          | 처리             |
|----------------|----------------|
| `OWNER`가 아님    | 권한 없음을 반환한다.   |
| 이미 `CLOSED` 상태 | 폐쇄된 조직임을 반환한다. |
