# 📝 4.4 가상 센서 관리

## 기능 목적

> 조직별 가상 센서 설정과 활성 상태를 Redis에 저장하고, 기기 Lock을 획득한 인스턴스가 `virtual-sensor-flow-{deviceEui}`를 실행하여 표준 데이터를 생성한다. 설정이 바뀌면 Flow를 재시작해 무중단으로 반영한다.

가상 센서는 **구역이 아니라 조직에 속한다.** 어느 구역에서 측정되는지는 만들어진 `deviceEui`를 구역 센서로 등록하는 순간 정해지며, 실제 센서와 똑같이 데이터를 만들 때마다 Inventory에 조회해서 채운다.

## Flow 구성

`VirtualSensorGeneratorNode` → `SensorZoneResolveNode` → `RabbitNormalizedPublisherNode`

- `VirtualSensorGeneratorNode`는 위치를 비운 채(`organizationId`/`storageId`/`zoneId` = null) 값만 만든다.
- `SensorZoneResolveNode`가 `deviceEui`로 구역을 해석해 위치를 채운다. 아직 구역에 등록되지 않았거나 구역·저장소가 비활성이면 그 데이터는 버린다.

## 입력값

| 항목 | 필수 | 설명 |
| --- | :---: | --- |
| `organizationId` | O | URL 경로의 조직 ID |
| `deviceEui` | O | 가상 장치 식별자 |
| `measurementIntervalSeconds` | O | 1초 이상의 생성 주기 |
| `virtualSensorValues.valueMap` | O | 센서 타입(`TEMPERATURE`/`HUMIDITY`/`DOOR`/`ILLUMINATION`)별 값 생성 설정, 1종 이상 |

`SensorValue`는 생성 모드에 따라 필요한 값이 달라진다.

| 모드 | 필수 값 | 사용 가능한 센서 |
| --- | --- | --- |
| `RANGE` | `min`, `max` (`min ≤ max`) | `door`를 제외한 전부 |
| `FIXED` | `fixedValue` | 전부. `door`는 0 또는 1만 허용 |
| `PROBABILITY` | `probability` (0~1) | `door`만 |

수정 요청(`VirtualSensorUpdateRequest`)에서 `measurementIntervalSeconds`는 생략하면 기존 값을 유지하고, `virtualSensorValues`는 필수라 보낸 값으로 교체된다(`VirtualSensorConfig.merge()`).

## 처리 절차

1. 생성 API가 설정값 형식을 검증한다(`OrganizationAccessService.verifyOwnerOrBoss`로 조직 오너/보스 권한도 확인).
2. 설정을 Redis(`rule-engine:virtual-sensor:config:{deviceEui}`)에 Lua `SETNX`로 중복 없이 저장하면서, 같은 트랜잭션에서 조직 색인(`rule-engine:virtual-sensor:organization:{organizationId}`)에도 추가한다.
3. 해당 `deviceEui`를 활성 목록(`rule-engine:virtual-sensor:active-devices`)에 추가한다.
4. `VirtualSensorCoordinator`가 갱신 주기(3초)마다 활성 목록을 확인하고, 등록 구역이 비활성인 기기는 목표 목록에서 뺀다.
5. 기기별 Redis Lease Lock(`rule-engine:lock:virtual-sensor:{deviceEui}`)을 획득한 인스턴스만 `virtual-sensor-flow-{deviceEui}`를 시작한다.
6. `VirtualSensorGeneratorNode`가 전용 데몬 스케줄러로 매 주기 설정된 센서 값을 생성하고, 문열림은 직전 상태와 달라졌을 때만 생성한다.
7. `SensorZoneResolveNode`가 위치를 채우고, `RabbitNormalizedPublisherNode`가 센서 키 기반 파티션 Normalized Queue에 발행한다.
8. Lock 갱신에 성공할 때마다 최신 설정을 다시 읽어, 실행 중인 설정과 다르면 Flow를 재시작해 반영한다.
9. 비활성화되거나 Lock을 잃으면 해당 Flow를 중지한다.

## API

기본 경로: `/api/rule-engine/organizations/{organization-id}/virtual-sensors`

| Method | 경로 | 권한 | 설명 |
| --- | --- | --- | --- |
| POST | `` | 오너·보스 | 가상 센서 설정 생성 및 활성화 |
| GET | `` | 조직원 | 조직의 가상 센서 목록(`deviceEui` 순) |
| GET | `/{device-eui}` | 조직원 | 가상 센서 단건 조회 |
| PUT | `/{device-eui}` | 오너·보스 | 설정 수정 |
| DELETE | `/{device-eui}` | 오너·보스 | 설정 삭제(활성 목록·조직 색인에서 함께 제거) |
| PUT | `/{device-eui}/status` | 오너·보스 | `ACTIVE` 또는 `INACTIVE` 변경 |

- 다른 조직의 `deviceEui`는 존재 여부조차 알려주지 않고 `VIRTUAL_SENSOR_CONFIG_NOT_FOUND`로 응답한다.
- 조회 응답에는 `registered`(설정 존재 여부), `status`, 구역에 등록되었다면 `zoneId`가 담긴다. `zoneId`가 `null`이면 아직 구역 센서로 등록되지 않아 생성한 데이터가 버려지고 있다는 뜻이다.
- 조회 응답의 `status`는 활성 목록에 있으면서 등록 구역도 활성일 때만 `ACTIVE`다. 화면에 실제로 도는 상태를 보여주기 위해서다.

## 설정 변경 무중단 반영

- `VirtualSensorCoordinator`는 `LeasedFlowOwner.onLeaseRenewed()`를 재정의해, Lock 갱신에 성공한 기기마다 Redis의 최신 설정을 다시 읽는다.
- 실행 중인 설정(`runningConfigs`)과 다르면 `restartFlow()`로 기존 Flow를 중지하고 최신 설정으로 새 Flow를 시작한다.
- 재시작은 해당 `deviceEui` Flow에만 영향을 주며, 다른 가상 센서나 수집·처리 Flow는 그대로 동작한다.
- 갱신 후 처리 도중 예외가 나면 소유권을 반납해, 다음 주기에 처음부터 다시 시작하게 한다.
- 소유권을 잃으면 `onOwnershipReleased()`에서 `runningConfigs` 항목도 함께 제거한다.

## 문열림 생성 방식

- 매 tick마다 `door` 설정(`PROBABILITY` 모드의 확률 또는 `FIXED` 값)으로 열림 여부를 다시 뽑는다.
- 직전에 전송한 상태(`lastDoorValue`, 초기값 `0.0` 닫힘)와 같으면 아무것도 발행하지 않는다.
- 값이 달라진 경우에만 발행하고 마지막 상태를 갱신한다. 실제 문 센서가 상태 변화 없을 때 데이터를 보내지 않는 동작과 동일하다.
- Flow가 재시작되면 `lastDoorValue`는 다시 "닫힘"으로 초기화된다.

## 완료 기준

- [x] 조직별 설정 생성·조회·수정·삭제와 활성·비활성 변경이 가능하다.
- [x] 설정 변경이 실행 중 Flow에 무중단으로 반영된다.
- [x] 같은 기기의 Flow가 중복 실행되지 않는다.
- [x] 가상 데이터가 실제 센서와 같은 파티션 Normalized Queue로 전달된다.
- [x] 선택한 센서 종류만 생성·발행된다(`valueMap`에 넣은 종류만).
- [x] 온도·습도·조도·문열림 4종과 `RANGE`/`FIXED`/`PROBABILITY` 생성 모드를 지원한다.
- [x] 가상 센서 위치가 실제 센서와 같은 경로(`deviceEui` → Inventory)로 해석된다.
- [x] 비활성 구역의 가상 센서 Flow는 자동으로 내려가고, 다시 활성화하면 살아난다.

## 현재 제약

- 설정 반영은 Lock 갱신 주기(3초)에 맞춰 이뤄지므로, API 호출 직후가 아니라 최대 한 주기 뒤에 적용된다.
- 구역 등록 여부는 Inventory 쪽 기기 등록 화면에서 처리한다. 룰엔진은 등록 결과를 조회만 한다.
- 구역이 비활성인 기기는 `ACTIVE`로 바꿀 수 없다(`VIRTUAL_SENSOR_ZONE_INACTIVE`). 아직 구역에 등록하지 않은 기기는 비활성 구역에 묶여 있지 않으므로 활성화를 막지 않는다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 이미 같은 `deviceEui` 설정이 있는데 생성 요청 | `VIRTUAL_SENSOR_CONFIG_EXISTS` 오류를 반환한다. |
| 설정이 없거나 다른 조직의 기기에 조회·수정·삭제·상태 변경 요청 | `VIRTUAL_SENSOR_CONFIG_NOT_FOUND` 오류를 반환한다. |
| 비활성 구역의 기기를 활성화 요청 | `VIRTUAL_SENSOR_ZONE_INACTIVE` 오류를 반환한다. |
| min > max, 확률 범위 초과, 주기 0 이하, `door`에 `RANGE` 모드 | 요청 검증 또는 `IllegalArgumentException`으로 거부한다. |
| 생성 주기 중 데이터 생성 실패 | 오류 로그만 남기고 스케줄러의 다음 실행을 계속한다. |
| 미등록·비활성 구역 기기의 데이터 | `SensorZoneResolveNode`가 그 자리에서 버린다(Flow는 정상 완료). |
| Flow 시작 실패 | Lock을 반납해 다른 인스턴스가 이어받게 한다. |
