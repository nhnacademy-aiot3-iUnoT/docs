# 📝 4.3 환경 룰 판단 관리

## 구현 상태

> `EnvironmentRuleEvaluationNode`, `DailyThresholdStatNode`, `EnvironmentStatusDecisionNode`가 `NormalizedSensorProcessingFlow`에 연결되어 실제 운영 경로에서 실행된다. 임계값·문열림 판단은 `ThresholdRuleCommand`/`DoorRuleCommand`(Command 패턴)로, 상태 판단은 `EnvironmentStatusDecisionNode`로 구현되어 있다. 임계값은 Inventory API에서 구역별로 조회한다.

## 룰 판단 구조

`EnvironmentRuleEvaluationNode`는 센서 타입을 `supports()`로 확인해 담당 `EnvironmentRuleCommand` 하나에 판단을 위임한다. 센서 타입을 지원하는 Command가 없거나 판단 결과가 비어 있으면 다음 노드로 보내지 않고 그 자리에서 Flow를 완료 처리한다.

| Command | 지원 센서 타입 | 판단 방식 |
| --- | --- | --- |
| `ThresholdRuleCommand` | `temperature`, `humidity`, `illumination` | 구역별 임계값 정책의 최소/최대 범위와 비교 |
| `DoorRuleCommand` | `door` | 구역에 문열림 룰이 설정된 경우에만, 값 자체로 즉시 판단 |

새 센서 타입이 임계값 기반으로 추가되면 `ThresholdPolicyDto`의 `ranges` Map에 항목만 추가하면 되고, 완전히 다른 판단 방식이 필요하면 `EnvironmentRuleCommand`를 구현한 새 Bean만 추가하면 된다.

## 임계값 정책 조회

`ThresholdPolicyService.getThresholdPolicy(zoneId)` → `InventoryClient.getThresholdPolicy(zoneId)` → `GET /api/core/internal/zones/{zoneId}/zone-threshold` 경로로 조회한다.

- 임계값은 구역에만 종속되고 `zoneId`가 전역 고유하므로 `zoneId` 하나가 곧 캐시 키다(`zone-threshold` 캐시, TTL 1분).
- 인벤토리는 센서 종류를 `TEMPERATURE`처럼 대문자로, 룰엔진은 `temperature`로 쓰므로 `SensorType.findByValue()`로 맞춘다. 지원하지 않는 종류의 임계값은 경고 로그를 남기고 건너뛴다.
- 응답 항목 하나는 `minValue`, `maxValue`, `alertDuration`(위반 지속 시간, 분)으로 구성된다. 한쪽 경계만 설정할 수 있다.
- 인벤토리에서 임계값이 변경되면 캐시 무효화 메시지(`zone-threshold`)가 Fanout으로 전파되어 즉시 반영된다.
- 최솟값 미만은 `BELOW_MIN`, 최댓값 초과는 `ABOVE_MAX`로 판단한다.
- 범위 안의 값은 `violated=false`(`NORMAL`) 결과를 생성한다.
- 해당 센서 타입의 범위가 정책에 없으면 판단을 건너뛴다(`Optional.empty()`).
- 임계값 CRUD 화면과 저장은 Inventory(장소 관리) 쪽 기능이며, 룰엔진은 조회만 한다.

## 문열림 검사

`DoorRuleCommand`는 `door` 센서만 처리한다.

- 구역의 임계값 정책에 `door` 항목이 없으면 검사를 건너뛴다(`Optional.empty()`). 문열림 알림을 켤지 여부를 구역 설정으로 제어한다.
- 값 `1.0`은 `OPEN`, 위반 상태(`violated=true`)로 판단한다.
- 값 `0.0`은 `CLOSED`, 정상 상태로 판단한다.
- 그 외 값은 지원하지 않는 상태로 기록하고 결과를 전달하지 않는다.
- 문 결과에는 `min`/`max`/`durationMinutes`가 없으므로 위반 시 즉시 `CRITICAL`로 전이한다.

## 하루 임계값 통계 집계

`DailyThresholdStatNode`는 판단 결과를 그 시점에 Redis로 하루 단위로 센다(4.8 하루 요약의 입력).

- 키는 `rule-engine:sensor-daily-stat:{zoneId}:{date}`이고, 센서 타입별로 `total`, `out`(이탈 건수), `min`, `max` 필드를 둔다. TTL은 3일이다.
- 하루의 경계는 `Asia/Seoul` 기준이며, `measuredAt`을 파싱하지 못하면 현재 시각으로 센다.
- 임계값이 없는 판단(`door` 등)은 이탈이라는 개념이 없어 세지 않는다.
- 통계는 수집 경로에 얹힌 부수 작업이라, 기록에 실패해도 경고 로그만 남기고 메시지는 다음 노드로 계속 흐른다.

## 환경 상태 판단

`EnvironmentStatusDecisionNode`는 `RuleResultDto`를 받아 구역 키와 센서 필드로 상태를 관리한다(`SensorKeys`).

- 구역 키: `organizationId:storageId:zoneId`
- 센서 필드: `deviceEui:sensorType`

상태(`EnvironmentDecisionState`)는 인스턴스 메모리가 아닌 **Redis Hash**(`rule-engine:env-status:state:{구역 키}`, field=센서 필드, TTL 3일)에 저장해 여러 인스턴스가 공유한다. 구역 단위 Hash로 저장하는 이유는 구역 환경 상태를 계산할 때 같은 구역 센서들의 상태를 한 번에 읽어야 하기 때문이다. 같은 센서 키의 메시지는 파티션 Queue의 `singleActiveConsumer` 덕분에 항상 하나의 컨슈머에서 순서대로 처리되므로, 읽기→판단→쓰기 구간에 별도 분산 Lock은 두지 않는다.

| 조건 | 상태 및 출력 |
| --- | --- |
| 측정 시각이 저장된 마지막 측정 시각보다 과거 | 상태 전이 없이 메시지를 버린다 |
| 측정 시각이 현재보다 1분(`FUTURE_TOLERANCE`) 넘게 미래 | 게이트웨이 시계 오차로 보고 상태 전이 없이 버린다 |
| 정상 결과 · 이전 상태 `NORMAL` | 상태만 갱신하고 이벤트를 만들지 않는다 |
| 정상 결과 · 이전 상태 `WARNING` 또는 지속 시간 조건이 없는 `CRITICAL` | 즉시 `NORMAL`로 해제하고 `STATUS_CHANGED` 이벤트 생성 |
| 정상 결과 · 지속 시간 조건이 있는 `CRITICAL` | 정상값이 지속 시간만큼 유지되어야 `NORMAL`로 해제한다. 대기 중에는 회복 시작 시각(`firstNormalAt`)만 기록 |
| 지속 시간(`durationMinutes`)이 없는 최초 위반 | 즉시 `CRITICAL`로 전이하고 `STATUS_CHANGED` 이벤트 생성 |
| 지속 시간이 있는 최초 위반(또는 이전 상태가 `NORMAL`) | `WARNING`으로 전이하고 `STATUS_CHANGED` 이벤트 생성 |
| `WARNING` 상태에서 위반 지속 시간 충족 | `CRITICAL`로 전이하고 `STATUS_CHANGED` 이벤트 생성 |
| 이미 `CRITICAL`인 상태로 30분(`ALERT_INTERVAL`) 경과 | `lastAlertAt` 갱신 후 `CRITICAL_REPEATED` 이벤트로 재출력 |
| 그 외(상태 유지) | `lastMeasuredAt`만 갱신하고 이벤트를 만들지 않는다 |

- 상태 값은 `NORMAL`, `WARNING`, `CRITICAL` 3단계다.
- 이벤트 사유는 `STATUS_CHANGED`, `CRITICAL_REPEATED` 2종이다.
- `measuredAt` 형식이 깨진 경우 메시지 처리 자체가 죽지 않도록 현재 시각(UTC)으로 대체하고 경고 로그를 남긴다.
- 상태 전이가 없으면 다음 노드로 메시지를 보내지 않는다(가장 흔한 경로).
- 구역이 비활성/종료되면 인벤토리가 캐시 무효화 메시지(`zone-decision-state`)를 보내고, `CacheInvalidationListener`가 그 구역의 판단 상태 Hash를 통째로 지운다. 남겨 두면 다시 켰을 때 상태 전이가 일어나지 않는다.

## 구역 환경 상태 반영

`ZoneEnvStatusReportNode` → `ZoneEnvStatusService`가 이벤트가 발생한 구역의 환경 상태를 Inventory에 반영한다.

- 구역 Hash에 저장된 센서 상태를 모두 읽어 심각도가 가장 높은 값(`NORMAL < WARNING < CRITICAL`)을 구역 상태로 삼는다.
- 직전에 보낸 값과 같으면 호출하지 않는다. 전송에 성공한 뒤에만 기억하므로, 실패하면 다음 이벤트에서 다시 시도된다.
- `PUT /api/core/internal/zones/{zoneId}/env-status?env-status=`로 갱신한다.
- 반영에 실패해도 경고 로그만 남기고 알림 발송은 계속된다.
- 알림은 구역 단위로 묶지 않고 센서별로 그대로 보낸다. 어느 센서가 문제인지 알아야 하기 때문이다.

## 파티션 기반 순서 보장

- `NormalizedSensorPublisher`는 `organizationId:storageId:zoneId:deviceEui:sensorType`을 해시해 2개 파티션 Queue 중 하나로 라우팅하며, 이 키는 `EnvironmentStatusDecisionNode`의 상태 키와 동일한 구성요소를 사용한다(`SensorKeys`가 양쪽 키 생성을 담당).
- 각 파티션 Queue는 `singleActiveConsumer`로 선언되어 항상 하나의 인스턴스만 소비하므로, 같은 센서의 연속 데이터가 항상 같은 인스턴스·같은 순서로 처리된다.
- 상태 자체는 Redis에 공유되므로, 파티션 재배치나 인스턴스 교체가 발생해도 최신 상태를 이어받아 판단할 수 있다.
- 미수신 센서 판단(일정 시간 데이터가 없을 때의 처리)은 구현하지 않았다.
