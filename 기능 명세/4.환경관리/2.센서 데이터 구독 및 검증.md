# 📝 4.2 센서 데이터 검증·저장·조회

## 기능 목적

> `NormalizedSensorProcessingFlow`가 실제·가상 센서의 표준 메시지를 소비하고, 검증·InfluxDB 저장부터 룰 판단·알림까지 이어지는 파이프라인의 앞단을 구성한다.

## Flow 구성

`NormalizedSensorConsumerNode` → `SensorPayloadValidationNode` → `DatabaseSaveNode` → `EnvironmentRuleEvaluationNode` → `DailyThresholdStatNode` → `EnvironmentStatusDecisionNode` → `EventCreateNode` → `ZoneEnvStatusReportNode` → `NotificationDispatchNode`

이 문서는 이 중 검증·저장·조회를 다루며, 룰 판단 이후 단계는 [4.3](./3.환경%20룰%20판단%20관리.md), [4.5](./5.환경%20이벤트%20및%20알림%20관리.md), [4.8](./8.환경%20리포트.md)에서 다룬다. Flow는 `NormalizedSensorFlowInitializer`가 `SmartInitializingSingleton`으로 Rabbit Listener 시작 전에 인스턴스마다 하나씩 등록·시작한다. 파이프라인은 `NormalizedSensorProcessingFlow.pipeline()`의 나열 순서대로 자동 배선된다.

## 처리 절차

1. `NormalizedSensorConsumerNode`가 파티션 Normalized Queue(`iunot.sensor.normalized.queue.0~1`)를 모두 구독하며 JSON을 `SensorPayload`로 역직렬화한다.
2. 메시지에 `FlowProcessingCompletion`을 담아 Flow의 출력 포트로 전달한다.
3. `SensorPayloadValidationNode`가 양수 ID(`organizationId`, `storageId`, `zoneId`), `deviceEui`, `sensorType`, `value`, `unit`, `time`을 검증한다.
4. `DatabaseSaveNode`가 `SensorInfluxService.save()`를 호출한다.
5. `SensorInfluxService`가 지원 센서 타입과 ID를 확인하고 측정 시각을 `Instant`로 변환한다.
6. InfluxDB에 식별값은 Tag, 측정값은 `value` Field로 저장한다.
7. 저장이 끝난 메시지는 이어서 `EnvironmentRuleEvaluationNode`로 전달된다(4.3 참고).
8. 어느 노드에서든 다음 노드로 메시지가 넘어가지 않으면 그 자리에서 완료 신호가 발생하고, Consumer는 최대 30초 동안 완료를 기다린 뒤 정상 반환해 Spring AMQP의 AUTO ACK 처리로 이어진다.

## 완료 신호 처리 방식

- `AbstractNode.process()`가 `onProcess()` 실행 후 "이번 호출에서 다음 노드로 메시지를 넘겼는지"를 스레드별로 추적해, 넘기지 않았으면 `Message.completeProcessing()`을 호출한다.
- 덕분에 룰 판단 결과가 없어 중간에 끝나는 메시지도 Consumer를 30초간 대기시키지 않는다.
- `onProcess()`가 예외를 던지면 완료 처리하지 않는다. `FlowEngine`이 예외를 잡아 `completeProcessingExceptionally()`로 실패를 알려야 Consumer가 재시도 여부를 판단할 수 있다.
- 연결되지 않은 출력 포트로 `send()`하면 메시지가 조용히 사라지고 완료로 오인된다. `Flow.validate()`가 기동 시점에 미연결 출력 포트를 오류로 잡는다.

## InfluxDB 저장 구조

| 구분 | 항목 |
| --- | --- |
| Tag | `organization_id`, `storage_id`, `zone_id`, `sensor_type`, `device_eui`, `unit` |
| Field | `value` |
| Timestamp | 센서 측정 시각(나노초 정밀도), 누락·오류 시 저장 시점의 현재 시각 |

## 조회 API

사용자 조회 경로는 조직 하위로 모여 있으며, `OrganizationAccessService`가 계정의 소속 조직과 구역 소유 조직을 검증한다.

| Method | 경로 | 설명 |
| --- | --- | --- |
| GET | `/api/rule-engine/organizations/{organization-id}/zones/{zone-id}/sensor-data/latest` | 구역의 센서 종류별 최신 데이터 |
| GET | `/api/rule-engine/organizations/{organization-id}/zones/{zone-id}/sensor-data/history` | 구역의 센서 이력 |
| GET | `/api/rule-engine/organizations/{organization-id}/storages/{storage-id}/sensor-data/latest` | 저장소 내 구역·센서별 최신 데이터 |
| GET | `/api/rule-engine/organizations/{organization-id}/sensor-data/latest` | 조직 내 저장소·구역·센서별 최신 데이터(`sensorType` 선택) |
| GET | `/api/rule-engine/internal/storages/{storage-id}/sensor-data/latest?organizationId=` | 인벤토리가 환경 현황을 구성할 때 호출하는 서버 간 경로(사용자 인증 없음) |

- 이력 조회는 `sensorType`, `from`, `to`, `window`를 선택적으로 사용한다. 기본 조회 기간은 종료 시각 기준 최근 24시간, `to`가 없으면 현재 시각, 기본 집계 주기는 `30m`다.
- 집계 주기는 `^[1-9]\d{0,3}[smhd]$` 형식만 허용한다(예: `1s`, `5m`, `1h`, `1d`).
- 최신 데이터 조회 범위는 최근 30일이다.
- 저장소 조회는 조직 태그까지 함께 걸어, 다른 조직의 저장소 번호로는 아무것도 조회되지 않는다.

## 완료 기준

- [x] 인스턴스마다 Normalized 처리 Flow가 자동 실행된다.
- [x] 실제·가상 센서가 동일한 Flow에서 검증·저장된다.
- [x] 저장 성공과 Flow 완료가 RabbitMQ Listener에 전달된다.
- [x] 최신 데이터 및 구역 이력 조회 API를 제공한다.
- [x] 내부 MQTT 의존성이 제거되었다.
- [x] 파티션 Queue를 모두 구독해 순서를 보장한 채 소비한다.
- [x] 중간에 끝나는 메시지도 노드 공통 로직으로 완료 처리된다.
- [x] 조회 API가 조직·구역 소유권 검증을 거친다.

## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| JSON 역직렬화 실패 | 오류를 기록하고 해당 메시지를 종료한다(완료 대기 없이 반환). |
| 센서 데이터 검증 실패 | 완료를 예외 처리하고 재큐잉하지 않는 `AmqpRejectAndDontRequeueException`으로 변환한다. |
| Flow 처리 30초 초과 | `AmqpException`으로 AMQP 처리 오류를 발생시킨다. |
| Flow 대기 중 스레드 중단 | 인터럽트 상태를 복원하고 `AmqpException`을 던진다. |
| 저장 또는 이후 단계(룰 판단·이벤트·알림) 처리 오류 | 완료를 예외 처리하고 AMQP 처리 오류를 발생시킨다. |
| 조회 조건 오류 | 잘못된 ID·시간 범위·집계 주기 오류를 반환한다. |
| 다른 조직의 조직·구역 조회 | `ORGANIZATION_ACCESS_DENIED` 또는 `ZONE_ACCESS_DENIED`로 거부한다. |
