# 📝 4.6 Flow 생명주기 및 설정 관리

## 기능 목적

> 세 종류의 Flow를 시작·중지하고, Local Connection의 비동기 처리를 관리하며 외부 수집과 가상 센서의 중복 실행을 방지한다.

## 현재 Flow

| Flow | ID | 생성 기준 | 시작 방식 |
| --- | --- | --- | --- |
| 외부 센서 수집 | `sensor-processing-flow` | 클러스터 전체 1개 | `ExternalIngressCoordinator`가 Redis Lease Lock 획득 후 시작 |
| 가상 센서 | `virtual-sensor-flow-{deviceEui}` | 활성 가상 센서별 1개 | `VirtualSensorCoordinator`가 기기 Lock 획득 후 시작 |
| 표준 센서 처리 | `normalized-sensor-processing-flow` | 인스턴스별 1개 | `NormalizedSensorFlowInitializer`가 `SmartInitializingSingleton`으로 Rabbit Listener 시작 전에 시작 |

- `sensor-processing-flow`는 `MqttSubscriberNode` → `SensorTransformNode` → `RabbitNormalizedPublisherNode` 3개 Node로 구성되며, 구역 해석과 표준 변환까지 이 Flow 안에서 끝난다.
- `virtual-sensor-flow-{deviceEui}`는 `VirtualSensorGeneratorNode` → `SensorZoneResolveNode` → `RabbitNormalizedPublisherNode` 3개 Node다. 실행 단위가 구역이 아니라 기기라는 점이 이전 구조와 다르다.
- `normalized-sensor-processing-flow`는 검증·저장뿐 아니라 룰 판단(`EnvironmentRuleEvaluationNode`), 하루 통계(`DailyThresholdStatNode`), 상태 전이(`EnvironmentStatusDecisionNode`), 이벤트 생성(`EventCreateNode`), 구역 상태 반영(`ZoneEnvStatusReportNode`), 알림 발송(`NotificationDispatchNode`)까지 하나의 Flow로 연결되어 있다. 배선은 `pipeline()` 목록의 나열 순서를 그대로 따른다.
- 내부 MQTT 설정, `SectionEnvironmentFlow` 계열 클래스, Raw Queue 경로(`RabbitRawPublisherNode`, `RawSensorConsumer`), `FlowCompletionNode`는 소스에서 제거되었다.

## Flow 소유권 공통 처리 (`LeasedFlowOwner`)

`ExternalIngressCoordinator`와 `VirtualSensorCoordinator`는 제네릭 추상 클래스 `LeasedFlowOwner<K>`를 상속해 Lock 기반 소유권 로직을 공유한다.

- `desiredKeys()`로 이번 주기에 소유해야 할 키 목록을 만들고, `reconcile()`이 갱신 주기(3초)마다 목표 상태와 현재 소유 상태를 맞춘다.
- 순서는 **자기 차단 → 목표 조회 → 불필요한 키 반납 → 보유 키 갱신 → 미보유 키 획득**이다.
- 자기 차단(fencing): 마지막 갱신 성공 후 `leaseDuration - renewInterval`(기본 10초 - 3초 = 7초)이 지나면 Redis 응답과 무관하게 스스로 Flow를 중지한다. Redis 장애로 갱신 요청 자체를 못 보낸 상황에서도 TTL 만료 전에 실행을 멈추기 위해 로컬 시각만 보고 판단한다.
- 갱신 실패(소유권 상실)는 즉시 Flow를 중지하지만, Redis 오류는 소유 상태를 유지하고 자기 차단이 처리하게 둔다. 일시적 장애로 Flow를 껐다 켜면 오히려 데이터가 끊기기 때문이다.
- 목표 조회(`desiredKeys()`)가 실패하면 그 주기를 통째로 건너뛴다. 조회 실패를 "대상 없음"으로 오인해 멀쩡한 Flow를 내리지 않기 위해서다.
- 하위 클래스 훅: `onLeaseRenewed()`(갱신 성공 후 설정 변경 확인), `onOwnershipReleased()`(로컬 상태 정리), `restartFlow()`(최신 설정으로 재시작).
- `ContextClosedEvent`를 받으면 소유 중인 모든 키의 Flow를 중지하고 Lock을 반납한다.

## RabbitMQ 구성

| 대상 | 구성 |
| --- | --- |
| 센서 Exchange | `iunot.sensor_exchange` (Direct, Durable) |
| Normalized Queue | `iunot.sensor.normalized.queue.0~1` (Durable, `singleActiveConsumer`) |
| 라우팅 키 | `iunot.sensor.normalized.0~1` |
| 캐시 무효화 Exchange | `iunot.cache_exchange` (Fanout, Durable) |
| 캐시 무효화 Queue | `iunot.cache.invalidation.queue.{instanceId}` (비영속·exclusive·autoDelete) |

- `NormalizedSensorConsumerNode`는 `@RabbitListener(queues = "#{@rabbitMqConfig.allNormalizedQueueNames()}")`로 모든 파티션을 구독하되, `singleActiveConsumer` 덕분에 실제로는 파티션마다 하나의 인스턴스만 소비한다.
- 발행 측(`NormalizedSensorPublisher`)은 센서 키를 해시해 항상 같은 파티션으로 라우팅하므로, 같은 센서의 메시지는 항상 같은 컨슈머 인스턴스로 순서대로 전달된다.
- `rule-engine.rabbitmq.queue-suffix` 값을 주면 Queue 이름과 라우팅 키 뒤에 접미사가 붙어, 같은 브로커에서 로컬·테스트 환경을 운영과 분리할 수 있다(dev 프로파일은 `-test`).

## 비동기 Flow 처리

- Flow Node 사이는 `LocalConnection`으로 연결한다. `transportConfig.capacity`를 주면 제한 버퍼, 없으면 무제한 버퍼다.
- `FlowEngine`은 Connection마다 가상 스레드 기반 소비 작업을 실행한다.
- Flow 시작 전 `validate()`가 Node·Port 존재 여부, 순환 연결, **연결되지 않은 출력 포트**를 검사한다. 미연결 출력 포트로 보낸 메시지는 조용히 사라지면서 완료로 오인되므로 기동 시점에 막는다.
- 동일 Flow ID는 한 인스턴스의 `FlowEngine`에 중복 등록하지 않는다(`ensureStarted`).
- `FlowProcessingCompletion`이 비동기 처리 결과를 RabbitMQ Consumer에 전달한다.
- 완료 신호는 별도 Node가 아니라 `AbstractNode.process()`가 처리한다. 다음 Node로 메시지를 넘기지 않은 Node가 그 자리에서 완료를 알린다.
- 검증, 저장, 룰 판단 등 어느 단계에서든 예외가 발생하면 Connection 작업이 완료 객체를 예외 상태로 변경한다.
- Flow 시작 중 예외가 나면 이미 만든 Connection 작업을 취소하고 Node를 정리한 뒤 예외를 다시 던진다.
- 종료 시 Connection 작업을 먼저 중단한 뒤 Node 자원을 종료하며, 하나가 실패해도 나머지는 반드시 정리한다.

## 설정 반영 범위

| 설정 | 저장소 | 반영 방식 |
| --- | --- | --- |
| 가상 센서 설정·활성 상태 | Redis | `VirtualSensorCoordinator`가 다음 확인 주기(3초)에 읽어 Flow 시작·중지·재시작 (4.4 참고) |
| 구역 임계값 | Inventory | `zone-threshold` 캐시(TTL 1분) + Fanout 캐시 무효화로 즉시 반영 |
| 기기 구역·구역 활성 여부 | Inventory | `device-zone`(30분/미등록 2분), `zone-activation`(30초), `zone-location`(30분/없는 구역 2분) 캐시 + Fanout 무효화 |
| 알림 수신자 | Inventory | 이벤트마다 조회(캐시 없음) |
| 환경 상태 판단 상태 | Redis | 인스턴스 간 공유, TTL 3일. 구역 비활성 시 Fanout 무효화로 초기화 |
| 이중화 Lock·주기 | `application.yaml` | `rule-engine.redundancy.*` |
| 하루 요약 배치 시각 | `application.yaml` | `rule-engine.daily-rollup.cron` (기본 `0 10 0 * * *`, Asia/Seoul) |

캐시 무효화는 Inventory가 `iunot.cache_exchange`에 `{cacheName, key}` 메시지를 발행하면, 각 인스턴스의 `CacheInvalidationListener`가 자신의 Caffeine 캐시 항목을 비우는 방식이다. `key`가 없으면 해당 캐시를 전부 비운다. `zone-decision-state`만 Caffeine이 아니라 Redis의 판단 상태 Hash를 지운다.

## 완료 기준

- [x] 외부 수집 Flow가 클러스터 전체에서 하나만 실행된다.
- [x] 활성 가상 센서별 Flow가 하나만 실행된다.
- [x] 각 인스턴스에서 Normalized 처리 Flow가 자동 실행되며 룰 판단·이벤트·알림까지 포함한다.
- [x] Flow Connection이 비동기로 처리되고 완료·오류가 Consumer에 전달된다.
- [x] 내부 MQTT 기반 Flow와 Raw Queue 경유 단계가 제거되었다.
- [x] Normalized Queue가 파티셔닝되어 센서별 처리 순서가 보장된다.
- [x] Lock 소유권 로직이 `LeasedFlowOwner`로 공통화되고 자기 차단이 적용되었다.
- [x] 가상 센서 설정 변경이 실행 중 Flow에 반영된다.
- [x] 룰(임계값)·구역 설정 변경이 캐시 무효화로 실행 중 Flow에 반영된다.
- [x] 미연결 출력 포트를 기동 시점에 잡아 조용한 데이터 유실을 막는다.
