# 📝 4.6 Flow 및 룰 설정 관리

## 기능 목적

> 위치 상태와 환경 설정에 따라 위치별 Flow의 생명주기를 관리하고, 서비스 중단 없이 환경 룰을 변경한다.


## 사용자 및 권한

- 환경관리 설정 권한을 가진 조직 관리자
- 환경관리 룰엔진 시스템
- 장소 관리 서비스


## 사전 조건

- 위치 정보와 활성 상태를 장소 관리 서비스에서 조회할 수 있어야 한다.
- 룰 및 가상 센서 설정을 데이터베이스에 저장할 수 있어야 한다.
- 공통 외부·내부 MQTT Flow가 실행 중이어야 한다.


## 입력값

| 항목 | 형식 | 필수 여부 | 설명 |
| --- | --- | :---: | --- |
| 위치 ID | Long | O | Flow 생성 및 관리 기준 |
| 병원명 및 위치명 | String | O | 위치별 Flow 정보 |
| 활성 센서 종류 | List\<String\> | O | 위치에서 사용하는 센서 목록 |
| 룰 설정 | Object | O | 임계값, 지속시간, 미수신 및 알림 설정 |
| 가상 센서 설정 | Object | X | 가상 센서 사용 위치에 적용 |
| 위치 상태 | String | O | Flow 생성, 중지 또는 제거 판단 기준 |


## 처리 절차

1. 룰엔진 시작 시 활성 위치와 가상 센서 설정을 조회한다.
2. 활성 위치마다 `location-rule-flow-{locationId}`를 생성하고 시작한다.
3. 가상 센서 사용 위치마다 `virtual-sensor-flow-{locationId}`를 생성하고 시작한다.
4. 위치가 비활성화되거나 삭제되면 해당 위치의 두 Flow를 중지하고 제거한다.
5. 룰 설정 변경 요청의 입력값과 사용자 권한을 검증한다.
6. 검증된 설정을 데이터베이스에 저장하고 실행 중인 Flow가 이후 데이터부터 새 설정을 사용하도록 반영한다.
7. Flow 생명주기와 룰 설정 변경 이력을 기록한다.


## 업무 규칙

- Flow ID에는 변경 가능한 병원명이나 위치명이 아닌 `locationId`를 사용해야 한다.
- 같은 `locationId`의 `LocationRuleFlow`와 `VirtualSensorFlow`를 중복 생성하지 않아야 한다.
- 위치별 Flow는 다른 위치의 Flow와 독립적으로 시작, 중지 및 제거할 수 있어야 한다.
- 위치가 비활성화되거나 삭제되어도 `external-sensor-flow`와 `internal-mqtt-subscriber-flow`는 계속 실행해야 한다.
- 서버 재시작 시 활성 위치와 저장된 설정을 기준으로 Flow를 자동 복구해야 한다.
- 룰 설정 변경을 위해 위치별 Flow를 삭제하거나 다시 생성하지 않아야 한다.
- 변경된 룰은 변경 이후 수신되는 센서 데이터부터 적용해야 한다.
- 룰 설정과 변경 이력은 데이터베이스에 저장되어 재시작 후에도 유지되어야 한다.
- 최소 임계값은 최대 임계값보다 클 수 없다.
- 이상 지속시간과 문열림 허용시간은 음수일 수 없다.
- 미수신 기준시간은 0보다 커야 한다.
- 지원하지 않는 센서 종류의 룰은 등록할 수 없다.


## 처리 결과

- 위치 상태에 맞는 환경관리 Flow가 생성, 시작, 중지 또는 제거된다.
- 서버 재시작 후 위치별 Flow와 설정이 복구된다.
- 실행 중인 서비스를 중단하지 않고 변경된 룰이 적용된다.
- Flow 및 룰 설정 변경 이력이 기록된다.


## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| 동일한 위치 Flow 생성 요청 | 추가 생성하지 않고 기존 Flow를 유지한다. |
| 필수 위치 정보 또는 설정 누락 | Flow 생성 또는 룰 변경을 거부하고 오류를 기록한다. |
| 유효하지 않은 임계값·시간 설정 | 저장하지 않고 검증 오류를 반환한다. |
| 지원하지 않는 센서 종류 | 룰 등록을 거부한다. |
| Flow 시작·중지·제거 실패 | 대상 위치와 Flow ID 및 실패 원인을 로그로 남긴다. |
| 서버 재시작 시 일부 Flow 복구 실패 | 다른 위치의 복구를 계속하고 실패한 위치를 기록한다. |
