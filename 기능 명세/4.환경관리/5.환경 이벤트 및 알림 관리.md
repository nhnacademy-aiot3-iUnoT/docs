# 📝 4.5 환경 이벤트 및 알림 관리

## 구현 상태

> `EventCreateNode`, `ZoneEnvStatusReportNode`, `NotificationDispatchNode`가 `NormalizedSensorProcessingFlow`에 연결되어 상태 전이마다 이벤트를 만들고 실제 채널로 알림을 발송한다. 웹 알림은 Inventory의 환경 이벤트로 저장되고, 텔레그램은 Bot API로 직접 전송한다.

## 기능 목적

환경 상태가 전이(`STATUS_CHANGED`, `CRITICAL_REPEATED`)되면 이상 이벤트를 생성하고, 구역별 수신자 설정에 따라 웹·텔레그램 채널로 알림을 전송한다.

## 처리 절차

1. `EnvironmentStatusDecisionNode`가 상태 전이를 판단하면 `EnvironmentEventDecisionDto`(이전 상태, 현재 상태, 사유)를 `RuleResultDto`와 함께 `EventCreateNode`로 전달한다.
2. `EventCreateNode`가 둘을 조합해 `EnvironmentStatusEventDto`(조직·저장소·구역·장치·센서·위반 유형·측정값·임계값·사유 포함)를 생성하고 로그로 기록한다.
3. `ZoneEnvStatusReportNode`가 구역 환경 상태를 Inventory에 반영한다(4.3 참고).
4. `NotificationDispatchNode`가 `NotificationRequest.from(event)`로 채널 공통 요청(제목·본문·발생 시각·메타데이터)을 만든다.
5. `NotificationPreferenceService.findPreferences(organizationId, storageId, zoneId)`로 수신자 목록을 조회한다.
6. `currentStatus`가 `WARNING`이면 발송하지 않는다. `WARNING`은 아직 확정되지 않은 관찰 단계라 알림을 보내지 않는다.
7. `enabled=true`인 설정마다 채널이 일치하는 `NotificationSender`를 찾아 발송한다.
8. `NotificationDispatchNode`는 출력 포트가 없는 종단 노드이므로, 여기서 처리가 끝나며 `AbstractNode`의 공통 로직이 완료 신호를 보내 RabbitMQ ACK로 이어진다.

## 이벤트 데이터

`EnvironmentStatusEventDto`는 `RuleResultDto`(측정·판단 정보)와 `EnvironmentEventDecisionDto`(상태 전이 정보)를 합친 구조다.

| 구분 | 항목 |
| --- | --- |
| 위치·장치 | `organizationId`, `storageId`, `zoneId`, `deviceEui`, `sensorType` |
| 판단 | `violationType`, `previousStatus`, `currentStatus`, `reason` |
| 측정 | `value`, `min`, `max`, `unit`, `measuredAt` |
| 설명 | `message` |

## 수신자 조회

`NotificationPreferenceService`는 두 종류를 합쳐 돌려준다.

- **웹 알림**: 개인 설정이 아니라 환경 이벤트 기록이므로 수신자와 무관하게 항상 한 건(`WEB`, `enabled=true`) 포함한다.
- **메신저 수신자**: 조직원이 직접 설정한 값이므로 `GET /api/core/internal/notifications/receivers?organization-id=&storage-id=&zone-id=`로 조회한다.
- 수신자 조회가 실패해도 경고 로그만 남기고 웹 알림(환경 이벤트 기록)은 그대로 남긴다.

`NotificationPreference`는 `userId`, 위치 3종, `channel`, `enabled`, `recipient`(채널별 수신자 식별자 — 텔레그램은 `chat_id`)로 구성된다.

## 알림 채널

지원 채널(`NotificationChannel`)은 `WEB`, `TELEGRAM` 2종이다. 설정에 있으나 구현체가 없는 채널은 로그만 남기고 건너뛴다.

| 채널 | 구현체 | 동작 |
| --- | --- | --- |
| `WEB` | `WebNotificationSender` | `POST /api/core/internal/environment-events`로 Inventory에 환경 이벤트를 저장한다 |
| `TELEGRAM` | `TelegramNotificationSender` | `POST https://api.telegram.org/bot{token}/sendMessage`로 제목+본문을 전송한다 |

### 웹 알림(환경 이벤트) 저장 조건

`EnvironmentEventCreateRequest.from()`이 조건을 만족할 때만 요청을 만든다.

- `violationType`이 `ABOVE_MAX` 또는 `BELOW_MIN`인 경우만 저장한다. 정상 복귀(`NORMAL`)와 문 상태(`OPEN`/`CLOSED`)는 인벤토리의 `BreachType`에 없어 텔레그램으로만 알린다.
- 임계값(`ABOVE_MAX`는 `max`, `BELOW_MIN`은 `min`)과 측정값이 모두 있어야 한다.
- 센서 타입은 인벤토리의 `EnvironmentType`으로 변환해 보낸다(`illumination` → `ILLUMINANCE`).

### 제목·본문 규칙

- 제목은 `currentStatus` 기준으로 `NORMAL` → "환경 상태 정상 복귀", `WARNING` → "환경 상태 경고", `CRITICAL` → "환경 상태 위험"이다.
- 본문은 저장소·구역·장치에 이어, `door`는 문 상태 문장("문이 열렸습니다." 등)을, 그 외 센서는 센서 타입·상태·측정값·단위·판단 메시지를 조합한다.
- 메타데이터에는 `value`, `unit`, `message`가 담긴다.

## 실패 격리

- 한 수신자에 대한 발송이 예외로 끝나도 잡아서 경고 로그만 남기고, 나머지 수신자와 센서 처리 Flow는 계속된다.
- 텔레그램은 `recipient`(chat_id)가 없으면 건너뛰고, API가 `ok=false`를 주거나 `RestClientException`이 나도 로그만 남긴다.
- 구역 환경 상태 반영 실패도 알림 발송을 막지 않는다.

## 남은 제약

- 카카오 등 추가 채널은 붙이지 않았다.
- 채널별 전송 결과를 별도 테이블로 기록하지 않는다. 성공·실패는 로그로만 남는다.
- 알림 발송이 Flow 안에서 동기로 일어나므로, 채널 응답이 느려지면 RabbitMQ ACK(30초 타임아웃)에 영향을 준다. 실패 복구용 재시도 큐는 없다.
- `EnvironmentStatusDecisionNode`의 `CRITICAL` 재출력 주기(30분)가 곧 재알림 주기다. 채널별로 다른 재전송 정책은 없다.
