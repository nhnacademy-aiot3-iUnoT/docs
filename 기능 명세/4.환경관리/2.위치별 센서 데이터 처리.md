# 📝 4.2 위치별 센서 데이터 처리

## 기능 목적

> 내부 MQTT로 수신한 표준 센서 데이터를 `locationId` 기준으로 위치별 환경관리 Flow에 분배하고 InfluxDB에 저장한다.


## 사용자 및 권한

- 환경관리 룰엔진 시스템
- 내부 MQTT 브로커
- 활성 상태의 위치에 생성된 `LocationRuleFlow`

## 사전 조건

- `internal-mqtt-subscriber-flow`가 실행 중이어야 한다.
- 처리 대상 위치가 활성 상태여야 한다.
- 해당 위치의 `location-rule-flow-{locationId}`가 생성되어 있어야 한다.
- InfluxDB 연결 정보가 설정되어 있어야 한다.


## 입력값

| 항목 | 형식     | 필수 여부 | 설명 |
| --- |--------|:-----:| --- |
| 표준 센서 데이터 | JSON   |   O   | 내부 MQTT `iot/#`에서 수신한 데이터 |
| 위치 ID | Long   |   O   | 위치별 Flow 분배 기준 |
| 센서 종류 | String |   O   | 저장 및 룰 판단 대상 센서 종류 |
| 측정값 | Number |   O   | 표준화된 센서 측정값 |
| 측정 시간 | String |   O   | ISO 8601 형식의 센서 측정 시간 |


## 처리 절차

1. 시스템 공통 Subscriber가 내부 MQTT의 `iot/#` 토픽을 구독한다.
2. 수신한 JSON을 `SensorPayloadDto`로 변환하고 필수값을 검증한다.
3. 메시지에서 `locationId`를 추출한다.
4. `location-rule-flow-{locationId}`를 찾아 메시지를 전달한다.
5. 위치 Flow의 ID와 메시지의 `locationId`가 일치하는지 다시 검증한다.
6. 센서 데이터의 측정 시간을 `Instant`로 변환한다.
7. 센서 데이터를 InfluxDB에 저장한다.
8. 정상 저장된 데이터를 환경 룰 판단 단계로 전달한다.


## 업무 규칙

- 내부 MQTT Subscriber Flow는 시스템 전체에서 하나만 실행해야 한다.
- 위치마다 MQTT Subscriber를 별도로 생성하지 않아야 한다.
- 활성 위치마다 `LocationRuleFlow`를 하나씩 운영해야 한다.
- 동일 위치의 Flow가 중복 생성되지 않아야 한다.
- 각 위치 Flow는 자신의 `locationId`와 일치하는 데이터만 처리해야 한다.
- InfluxDB Tag에는 병원명, 위치 ID, 위치명, 센서 종류, 장치명 및 장치 식별자를 저장해야 한다.
- InfluxDB Field에는 측정값을 저장해야 한다.
- 측정 시간이 있으면 해당 시간을 사용하고, 없으면 서버 수신 시간을 사용할 수 있다.
- 한 위치 Flow의 오류가 다른 위치 Flow에 영향을 주지 않아야 한다.
- 저장 실패 후 룰 판단을 계속할지는 시스템 정책으로 일관되게 관리해야 한다.

## 처리 결과

- 센서 데이터가 위치별 `LocationRuleFlow`로 전달된다.
- 위치 및 장치 정보를 포함한 시계열 데이터가 InfluxDB에 저장된다.
- 저장된 데이터가 환경 룰 판단 대상으로 전달된다.


## 예외 처리

| 예외 조건 | 처리 |
| --- | --- |
| JSON 변환 실패 또는 필수값 누락 | 메시지를 처리하지 않고 경고 로그를 남긴다. |
| `locationId`가 없음 | 위치별 Flow로 전달하지 않는다. |
| 대상 위치 Flow가 없음 | 메시지를 처리하지 않고 위치 ID와 경고 로그를 남긴다. |
| Flow 위치 ID와 메시지 위치 ID가 다름 | 다음 노드로 전달하지 않고 경고 로그를 남긴다. |
| InfluxDB 저장 실패 | 위치, 센서 종류 및 장치 정보를 포함한 오류 로그를 남긴다. |
