# 📝 14. AI 발주 추천 브리핑

## 기능 목적

> 출고 이력을 분석해 다음 주에 발주가 필요한 의약품과 권장 수량을 산출하고,
> 매일 아침 저장소별 브리핑으로 제공한다. 챗봇으로도 즉시 조회할 수 있다.

## 사용자 및 권한

- 저장소 조회 권한을 가진 사용자 (기존 챗봇 툴과 동일 기준)
- 조회 전용 기능이며, 재고를 변경하지 않는다.

## 사전 조건

- 대상 저장소에 `stock_transactions` 출고(OUTBOUND) 이력이 존재한다.
- 권장 수량 정확도를 위해 `stock_thresholds`가 설정되어 있는 것이 바람직하다. (미설정 시 안전재고 0으로 계산)

## 범위

| 포함 | 미포함 |
|---|---|
| 출고 이력 기반 발주 필요량 산출 | 실제 입고 처리 (자연어 입고는 별도 작업에서 진행) |
| 매일 아침 저장소별 브리핑 생성 | 발주서 생성 / 외부 발주 시스템 연동 |
| 챗봇 툴을 통한 즉시 조회 | 재고를 변경하는 모든 동작 |

## 처리 절차

### 산출 로직

집계 단위: **`medicinePackageUnit` × `storage`**
(`stock_transactions`는 `zone` 기준이므로 `zone.storage`로 롤업 — `sumByType()` 방식과 동일)

1. 최근 4주 `OUTBOUND` 합계 → `주간평균소비 = 합계 / 분석주수`
2. 최근 1주 `OUTBOUND` 합계 → `추세계수 = 최근1주 / 주간평균`
3. `다음주예상소비 = 주간평균 × clamp(추세계수, 0.5, 2.0)`
4. `가용재고 = 현재재고 합 − 다음주 내 유통기한 만료분`
5. `안전재고 = StockThreshold.threshold` (`isActive = true`)
6. `기본부족량 = 다음주예상소비 + 안전재고 − 가용재고`
7. **폐기 하향 조정** (아래 참조)
8. `부족량 > 0`인 품목만 반환, 예상 소진일수 오름차순 정렬

### 거래 유형별 취급

| 유형 | 처리 | 사유 |
|---|---|---|
| `OUTBOUND` | 소비량 본체 | 실수요 |
| `DISPOSAL` | 하향 조정 계수로만 사용 | 수요가 아니라 과잉 발주 신호 |
| `INBOUND` | 직전 입고일 표시용 | |
| `TRANSFER_OUT` / `TRANSFER_IN` | 제외 | 조직 내 이동, 총량 불변 |
| `INFO_CORRECTION_OUT` / `IN` | 제외 | 재고 정정, 수요 아님 |

### 폐기 하향 조정

폐기는 수요에 더하지 않는다. 폐기가 많다는 것은 그동안 과잉 발주했다는 신호이므로,
다음 발주 권장 수량을 낮추는 방향으로 반영한다.

```
폐기율   = 기간 DISPOSAL(만료) / (OUTBOUND + DISPOSAL(만료))
조정계수 = 1 - min(폐기율, 0.5)      // 최대 50%까지만 감액
권장수량 = ceil(기본부족량 × 조정계수)
```

- 상한 0.5를 두는 이유: 폐기율 이상치로 권장 수량이 0이 되어 실제 필요한 발주를 놓치는 것을 방지
- **만료성 폐기만 대상으로 한다.** `StockTransaction.reason`에 `DisposalReason.name()`이 저장되므로 `reason = 'EXPIRED'`로 필터한다. `DETERIORATED`(변질) / `OTHER`는 사고이지 과잉 재고 신호가 아니다.
- 조정이 적용되면 브리핑 문구에 사유를 함께 노출한다.
  예) `※ 최근 폐기 12개(폐기율 8%)를 반영해 권장 수량을 하향했습니다.`

### 방어 케이스

| 상황 | 처리 |
|---|---|
| 분석 기간 출고 0 | 추천 대상에서 제외 (신규/미사용 품목) |
| 주간평균 0 | 예상 소진일수 `null` (0으로 나누기 방지) |
| `StockThreshold` 미설정 | 안전재고 0으로 계산 + `thresholdConfigured = false` |
| 이력이 분석 기간보다 짧음 | 실제 데이터 존재 기간으로 나누고 `dataWeeks`를 응답에 포함 |
| 접근 가능 저장소 없음 | 즉시 빈 결과 반환 |

## 아침 브리핑

### 전달 방식

챗봇은 `POST` 단방향이고 Redis 대화 맥락 TTL이 1시간이므로 **서버 → 클라이언트 푸시가 불가능하다.**
따라서 푸시가 아니라 **당겨오기(pull)** 로 구현한다.

1. 매일 아침 9시 배치가 저장소별 브리핑을 DB에 생성
2. 사용자가 챗봇 패널을 열 때 오늘자 브리핑을 조회해 assistant 말풍선으로 표시

사용자 경험은 "아침에 챗봇이 알려준 것"과 동일하고, 로그인 시각과 무관하게 놓치지 않는다.

### 브리핑 생성은 LLM을 사용하지 않는다

저장소 수만큼 LLM을 호출하면 비용이 비례해 늘고, API 실패 시 그날 브리핑이 통째로 유실된다.
`ExpirationAlertScheduler`와 동일하게 **Java에서 문자열로 조립**한다. 결정적이고, 비용이 없고, 단위 테스트가 가능하다.
사용자가 근거를 되물으면 그때 LLM이 `getReorderSuggestion` 툴을 호출한다.
→ **배치는 알림, 챗봇은 대화**로 역할을 분리한다.

### 스케줄

```java
@Scheduled(cron = "0 0 9 * * MON-FRI", zone = "Asia/Seoul")   // 발주는 평일 업무
@SchedulerLock(name = "createDailyReorderBriefing",
               lockAtLeastFor = "PT5M", lockAtMostFor = "PT20M")
```

- ShedLock 필수. 인스턴스가 2대면 브리핑이 2번 생성된다. `ShedLockConfig`가 이미 존재하므로 설정 추가는 없다.
- **타임존을 명시한다.** 서버가 UTC면 실제 실행이 오후 6시가 된다.
- 순회: `ACTIVE 조직 → ACTIVE 저장소 → analyze(List.of(storageId)) → 결과 있으면 저장`
- 결과 0건인 저장소는 저장하지 않는다 (빈 브리핑은 노이즈).

### 브리핑 단위 — 저장소별 1건

- `UNIQUE(storage_id, briefing_date, briefing_type)` 으로 재실행 멱등성 보장
- 문구 헤더에 저장소명을 포함: `[본원 약제창고] 발주 추천 (9/5 기준)`
- 조회 API는 `storageName` 오름차순 정렬 리스트를 반환
- **말풍선 상한**: 접근 저장소가 많으면 패널 열자마자 스크롤이 밀린다.
  `itemCount` 내림차순 상위 5건만 표시하고 나머지는 "외 N개 저장소" 한 줄로 접는다.
  (`itemCount` 컬럼을 두는 이유 — 정렬하려고 `content`를 파싱하지 않기 위함)
- 30일 경과 브리핑 정리 배치 1개 필요

## 설계 제약: 스케줄러는 `UserContext`를 사용할 수 없다

`ChatbotStorageAccessService.getAccessibleStorageIds()`는 `UserContext.getUserUuid()`에 의존한다.
스케줄러 스레드에는 요청 컨텍스트가 없어 그대로 호출하면 실패한다.

```
ReorderSuggestionService.analyze(storageIds, weeks)   ← storageIds를 파라미터로 받음. UserContext를 모른다
        ├── ReorderSuggestionTool      → accessService로 storageIds를 구해 호출 (요청 스레드)
        └── ReorderBriefingScheduler   → 조직/저장소를 순회하며 호출 (스케줄러 스레드)
```

**`analyze()`가 `UserContext`를 절대 참조하지 않는다** — 이 규칙만 지키면 툴과 스케줄러가 계산 로직을 100% 공유한다.

## 챗봇 툴

두 요구사항(입고 추천 / 출고량 분석)은 같은 계산의 입력과 출력이므로 **툴 1개**로 합친다.
분리하면 LLM이 두 번 호출해 숫자를 스스로 조합하다 틀린다.

```java
@Tool(name = "getReorderSuggestion", description = """
    최근 출고 이력을 분석해 다음 주에 발주가 필요한 의약품과 권장 수량을 계산합니다.
    사용 예시
    - 다음주에 뭐 발주해야 해?
    - 발주 추천해줘 / 입고 추천해줘
    - 출고량 기준으로 부족할 재고 알려줘
    저장소명과 분석 주 수는 선택사항입니다. (분석 주 수 기본 4주, 최대 12주)
    """)
```

파라미터: `storageName`(optional), `analysisWeeks`(optional, `Math.clamp(1, 12)`)

### 시스템 프롬프트 추가분

```
getReorderSuggestion 결과:
의약품명, 권장 발주 수량, 현재 재고, 주간 평균 출고량, 예상 소진일수를 안내하세요.
권장 수량과 예상치는 과거 출고 이력 기반 추정이며 참고용임을 함께 알리세요.
결과에 없는 품목을 임의로 추가하거나 수량을 직접 계산하지 마세요.
분석 기간이 요청보다 짧으면(데이터 부족) 실제 분석 기간을 먼저 알리세요.
```

마지막 줄이 중요하다. 이 툴은 계산된 숫자를 반환하므로 LLM이 재계산을 시도하면 즉시 틀린다.

## 응답 DTO

근거 필드가 없으면 LLM이 "왜 이 수량인가"를 지어낸다.

```java
record Item(
    String productName, String packUnit, String storageName,
    int suggestedQuantity,        // 권장 발주량
    int currentQuantity,          // 현재 가용 재고
    int expiringSoonQuantity,     // 다음주 만료 예정 (가용에서 제외된 양)
    double weeklyAverageOutbound, // 주간 평균 출고
    int lastWeekOutbound,         // 최근 1주 출고 (추세 근거)
    int disposalQuantity,         // 분석기간 만료 폐기량
    double disposalRate,          // 폐기율
    boolean adjustmentApplied,    // 하향 조정 적용 여부
    Integer threshold,            // null이면 미설정
    Integer daysUntilStockout,    // null이면 산출 불가
    LocalDate lastInboundDate
)
```

`processedBy`(처리자 UUID)는 조회하지 않는다. 챗봇 응답에 담당자 개인정보가 노출될 이유가 없다.

## 쿼리 설계

QueryDSL로 주(week) 버킷을 만들면 DB 함수(`YEARWEEK`)에 종속되어 테스트가 깨진다.
**기간을 나눠 두 번 집계**하는 편이 단순하고 안전하다.

| # | 메서드 | 기간 |
|---|---|---|
| 1 | `sumOutboundByUnit(storageIds, from, to)` | 최근 4주 |
| 2 | `sumOutboundByUnit(storageIds, from, to)` | 최근 1주 (동일 메서드 재사용) |
| 3 | `sumExpiredDisposalByUnit(storageIds, from, to)` | 최근 4주, `reason = 'EXPIRED'` |
| 4 | `findStockPositions(storageIds, packageUnitIds, expiryLimit)` | 재고 · threshold · 임박분 |

조인은 Java에서 수행한다.
`sumByType()`의 `zone.storage.id.in(...)` + `processedAt` 범위 패턴을 그대로 차용하고,
`storageIds`가 비면 즉시 `List.of()`를 반환하는 가드도 기존 툴과 동일하게 적용한다.

권장 인덱스: `stock_transactions (zone_id, transaction_type, processed_at)`

| 예외 조건 | 처리 |
|---|---|

| 배치 중 특정 저장소 산출 실패 | 해당 저장소만 건너뛰고 로그 기록, 나머지 계속 진행 |
